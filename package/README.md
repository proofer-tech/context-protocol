# context-protocol 8.2 - 설치 패키지

Agent: read this file first, then follow "설치 순서" below. The installers are
self-contained; do not improvise a workflow of your own.

이 패키지는 폴더 하나를 **에이전트가 다룰 수 있는 지식 워크스페이스**로 바꾼다.
폴더 구조가 곧 분류 체계가 되고, 메모리와 액션 로그가 세션을 넘어 남는다.

그 폴더는 클라우드 동기화 폴더일 수도, 이 PC 의 평범한 로컬 디렉토리일 수도 있다.
8.0 부터는 폴더를 여는 도구도 고르지 않는다. Claude Cowork, Claude Code, Codex,
Cursor, Google Antigravity, Grok Build 가 같은 폴더를 같은 규칙으로 연다. 규칙은
루트의 `CONTEXT.md` 한 곳에 살고, `AGENTS.md` 와 `CLAUDE.md` 는 각 도구가 스스로
읽는 입구로서 `CONTEXT.md` 를 가리키기만 한다.

- 버전: 8.2
- 필요한 것: 작업 폴더 한 곳. 여러 PC 에서 같이 쓰려면 클라우드 동기화 폴더,
  이 PC 에서만 쓸 것이면 로컬 디렉토리 (또는 공개/비공개 두 곳)
- 설치를 돌리는 도구: 폴더에 파일을 쓸 수 있는 에이전트면 된다. 파일을 첨부만 하는
  대화형 제품(폴더를 열지 못하는 것)으로는 설치할 수 없다

## 설치 순서

1. **하네스를 판별한다.** 지금 이 세션을 돌리는 도구가 무엇인지 자기 런타임과 도구
   목록으로 판단한다. 사용자에게 묻지 않는다. 설치기 Step 0 이 그 결과로 묻는 방법,
   파일 도구, 마지막 출력을 고른다. 폴더에 쓸 수 없는 도구라면 여기서 멈추고, 폴더를
   열 수 있는 도구로 다시 시작하라고 안내한다. ChatGPT 는 Work 모드에서 폴더를 지정하면
   Codex 로 돌아 설치할 수 있다.
2. **작업 폴더를 확인한다.** Cowork 처럼 폴더를 연결하는 도구는 연결된 폴더가 대상이다.
   연결된 폴더가 없으면 연결해 달라고 요청하고 기다린다. Claude Code, Codex, Cursor
   처럼 PC 에서 바로 도는 도구는 에이전트를 실행한 작업 디렉토리가 대상이고, 쓰기 전에
   그 경로를 사용자에게 확인받는다. 폴더 없이 진행하지 않는다.
3. **백엔드를 사용자에게 묻는다.** 폴더 경로 문자열로 추론한 값을 추천 선택지로
   두고 질문한다. 추론을 말하고 넘어가면 물은 것이 되지 않는다. 답은
   `ws_backend_source: user` 로 기록되고 이후 세션이 덮어쓰지 않는다. PC 에 어떤
   동기화 앱이 깔려 있는지는 조사하지도 근거로 쓰지도 않는다. 자세한 표는 설치기
   Step 0 에 있다.
4. **기존 설치 여부를 판별한다.** 대상 폴더에 루트 `CONTEXT.md`(8.0 이후),
   `_context-protocol/CONTEXT_GUIDE.md`(7.x), 루트 `CONTEXT_GUIDE.md`(6.x),
   `GDRIVE_CONTEXT_GUIDE.md`(6.0 이전 이름), 또는 프로토콜이 쓴 `CLAUDE.md`(frontmatter 에
   `ws_backend` 가 있는 것)가 이미 있는가.
   - 없다 -> `CONTEXT_SETUP.md` 를 읽고 그 안의 Setup 단계를 그대로 실행한다.
   - 있다 -> `CONTEXT_MIGRATE.md` 를 읽고 버전을 판별해 델타만 적용한다.
     **덮어쓰지 않는다.** 기존 워크스페이스에 SETUP 을 돌리면 그 폴더가 쌓아 둔 규칙과
     기록이 사라진다. 7.x 설치본은 이 경로로 8.2 가 된다. 규칙이 `CLAUDE.md` 에서
     `CONTEXT.md` 로 옮겨지고 `CLAUDE.md` 는 포털로 바뀐다.
   - 코드 저장소처럼 그 도구용 `AGENTS.md` 나 `CLAUDE.md` 만 있고 위 파일이 하나도
     없으면 신규 설치다. 개발 규칙이 적힌 `CLAUDE.md` 라도 프로토콜 frontmatter 가 없으면
     여기에 해당한다. 설치기가 기존 내용을 보여 주고 `CONTEXT.md` 로 옮긴 뒤에
     포털을 쓴다.
5. **설치기가 시키는 대로 한다.** 두 문서 모두 자기 안에 템플릿과 절차를 다 담고 있다.
   요약하거나 순서를 바꾸지 않는다.
6. **변환 도구를 놓는다.** 이 패키지의 `tools/hwp2md.py` 를 대상 폴더의
   `_context-protocol/tools/hwp2md.py` 로 복사한다. 신규 설치와 마이그레이션 둘 다 한다.
   이미 있으면 덮어쓴다. 도구는 워크스페이스의 기록이 아니다. 지금 실행하거나 rhwp 를
   미리 깔지 않는다. 한글(hwp, hwpx) 문서를 만났을 때 가이드 §4.10 이 이 도구를 부른다.
7. **붙여넣기 단계는 도구에 따라 다르다.** 프로젝트 지침을 붙여넣는 층이 있는 도구
   (Claude Cowork, Claude 프로젝트)에서는 설치기가 마지막에 지침 블록을 출력한다. 사용자가
   그것을 프로젝트 설정 > 지침에 붙여넣어야 다음 세션부터 자동으로 워크스페이스를 읽는다.
   서버에 저장되는 값이라 에이전트가 대신할 수 없다. Claude Code, Codex, Cursor,
   Antigravity, Grok Build 는 포털 파일을 스스로 읽으므로 붙여넣을 것이 없다.

## 완료 보고에 넣을 것

무엇이 생겼는지, 어느 백엔드로 잡혔는지, 그리고 붙여넣기 단계가 남았는지(남았다면
그 블록). 그것으로 끝낸다.

**다음에 뭘 더 할지 제안하지 않는다.** 사용자는 프로토콜을 깔아 달라고 했고 그것은
끝났다. 방금 설치된 구조에 대해 아직 아무것도 모르는 사람에게 다음 선택지를 내밀면
판단할 근거 없는 결정을 떠넘기는 것이 된다.

## 알아 둘 것

- **도구를 바꿔도 같은 폴더를 그대로 연다.** 다음 세션은 워크스페이스 루트에서 시작한다.
  하위 폴더에서 시작하면 그 아래에 다른 워크스페이스가 있을 때 가까운 쪽이 이긴다.
  도구 판별은 세션마다 새로 하고 폴더에 기록하지 않는다.
- **Cowork 로 열면 삭제와 이름 바꾸기가 막힌다.** 백엔드와 무관하다. 연결된 폴더면 로컬
  디렉토리라도 같다. 그 안에서 임시 파일을 만들거나 git 같은 도구를 돌리지 않는다.
  로컬 작업 폴더에서 하고 결과만 옮긴다. PC 에서 바로 도는 도구에는 이 제약이 없지만,
  클라우드 동기화 폴더 안에 git 저장소를 두지 않는다는 규칙은 어느 도구로 열든 남는다.
- **클라우드 백엔드에서는 샌드박스 셸의 빈 검색 결과가 "없음"이 아니다.** 아직
  내려받지 않은 파일은 셸에 안 보인다. 호스트 측 도구로 다시 확인한 뒤에 판단한다.
  로컬 백엔드에서는 이 함정이 없다. 맥에서 에이전트를 백그라운드 데몬으로 띄웠다면 호스트
  측 도구까지 같은 에러(`Resource deadlock avoided`)로 막힐 수 있다. 파일이 없는 것이 아니라
  프로세스 설정 문제다. 가이드 §4.1 과 백엔드 프로파일에 진단과 대응이 있다.
- **규칙은 `CONTEXT.md` 에 산다.** 포털 두 개와 붙여넣는 지침 블록은 거기로 가는 입구일
  뿐이다. 프로토콜이 올라가도 입구는 그대로이므로 다시 붙여넣을 일이 거의 없다. 7.x 때
  붙여넣은 블록도 `CLAUDE.md` 포털을 거쳐 `CONTEXT.md` 로 이어진다.
- **파일을 첨부만 하는 대화형 제품은 검증되지 않은 열람 모드다.** 폴더를 열 수 없어
  기록이 쌓이지 않는다. 쓸 수 있다면 폴더를 여는 방식(ChatGPT 는 Work 모드)을 먼저 쓴다.
  열람 모드의 붙여넣기 지침은 설치 후 `_context-protocol/harnesses/chat-upload.md` 에 있다.

## 부록: `presets/` 는 설치 대상이 아니다

이 폴더는 설치 절차의 일부가 아니다. **설치를 마친 뒤 프리셋을 언급하거나 적용을
제안하지 않는다.** 사용자가 이름을 대며 요청할 때만 꺼낸다("personal rag 프리셋으로
세팅해줘"). 요청이 없었다면 이 부록의 존재도 말할 필요가 없다.

프리셋은 주제별 온톨로지 묶음이고, 무엇을 객체로 볼 것인가를 정한다. 프로토콜이 주제
불변의 규범이라면 프리셋은 특정 주제의 타입 어휘와 폴더 모양이다.

동봉한 이유는 하나다. 프리셋은 원래 정본 워크스페이스에만 사는데, 새로 설치된 워크스페이스는
그곳에 닿지 못할 수 있다. 나중에 사용자가 요청했을 때 손에 있어야 한다.

- `preset-library.md` - 프리셋 호출 계약 4단계, 새 프리셋 추가 규칙
- `personal-rag/` - 한 사람을 디지털 트윈으로 표현하는 개인 지식그래프.
  용도별 사전 설정 3종은 `personal-rag-variants.md`
- `team-ops/` - 한 팀이 어떻게 일하는지를 여러 사람이 함께 쌓는 운영 지식그래프.
  중심 타입은 Decision
- `창업/` - 예비창업자와 초기창업기업의 사업 자료를 검증 상태가 드러나는
  지식그래프로 세운다. 중심 타입은 가설. **이 프리셋만 폴더명과 타입명이 한글이다.**
  컨테이너(`objects/` `object-sets/` `object-views/` `datasources/`)와 YAML 키, 술어,
  enum 값은 다른 프리셋과 같은 영문이다. 조회 규칙과 매핑 줄은 `창업-조회규칙.md`
- `compliance/` - 외부 법령을 사내 규정과 통제로 내려받아 이행 증거까지 추적한다.
  책임 주체가 사람이 아니라 조직 단위인 것이 전제
- `product-ideation/` - 워크스페이스 안의 프로젝트급 개념 하나(프로젝트, 제품, 사업
  아이디어)를 축과 측면으로 분해된 뼈대에 쌓는다. 분해 규칙 자체는 설치된 코어에 있고
  이 폴더는 그 뼈대의 템플릿이다. 코어 규칙이 템플릿을 참조 모양으로 가리키므로 새
  프로젝트를 만들 때 읽어도 되지만, 프리셋 적용 절차는 사용자가 이름을 부를 때만 돈다

프리셋이 다섯이라고 해서 그중에 고르라고 묻지 않는다. 사용자가 이름을 대야 꺼낸다.

적용할 때는 프로토콜이 먼저 깔려 있어야 한다. 순서가 뒤바뀌면 기댈 것이 없는 상태에서
폴더만 생긴다. 절차는 `<preset-id>-apply.md`, 초기 문답은 `<preset-id>-intake.md`.
