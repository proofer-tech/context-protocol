# 스킴 확장

대상 워크스페이스의 `_context-protocol/_schema/concept-scheme.md` 에 병합할 확장이다. 코어 스킴의
허용 노트 타입과 술어에 아래를 **추가**하고, 코어 규칙은 그대로 둔다.

술어와 값 타입은 폴더를 소유할 수 없는 스키마라 한 파일에 모았다. 헤드리스 에이전트
에게는 한 번 읽어 어휘 전체를 확보하는 편이 낫다. [[personal-rag-schema]],
[[team-ops-schema]] 와 같은 구성이다.

## 허용 노트 타입 추가

코어의 concept / document / schema / project-descriptor / readme / view / proposal 에
객체 타입 8개를 추가한다.

```
사업체, 제공물, 고객군, 가설, 근거, 마일스톤, 자금, 제출문서
```

이 8개는 lint 상 **document 와 동일하게** 취급한다. 소속이 결정돼야 하고 `broader` 는
갖지 않는다.

## 다른 프리셋과 실체가 겹치는 타입

**타입명 충돌은 한글화로 사라졌다.** 2026-09-16 이전에는 이 프리셋의 타입명이 영문이라
`Evidence` 가 [[compliance]] 와, `Artifact` 가 [[personal-rag]] 와 문자열까지 같았다.
지금은 `근거` 와 `제출문서` 라 같은 워크스페이스에 얹어도 폴더와 개념 id 가 부딪히지 않는다.

**다만 실체가 가까운 것은 그대로다.** 이름이 갈렸다고 구분이 저절로 서는 것은 아니다.

| 이 프리셋 | 가까운 것 | 무엇이 다른가 |
|---|---|---|
| `근거` | compliance 의 `Evidence` | 저쪽은 통제(Control)가 이행됐음을 보이는 증적이다. 감사 대응이 목적이고 보존 기간과 제출 대상이 붙는다. 이쪽은 가설을 지지하거나 반증하는 관측이고 `sampleSize` 가 필수다. 교집합이 `collectedAt` 하나다 |
| `제출문서` | personal-rag 의 `Artifact` | 저쪽은 개인이 만든 결과물 전반(글, 코드, 사진)이다. 이쪽은 제출용 문서에 한정되고 `version` 과 `submittedTo` 가 본체다 |

**그래도 둘 이상을 한 워크스페이스에 얹지 않는 것을 권장한다.** 이름이 안 부딪혀도 사람이
헷갈리고, 조회 규칙이 두 벌 붙으면 어느 쪽 규칙으로 답해야 하는지가 안 정해진다.

굳이 병행한다면 이름은 이미 갈라져 있으므로 바꿀 것이 없고, 대신 대상 워크스페이스
`CONTEXT.md` 에 **어느 질의가 어느 쪽으로 가는지**를 한 절로 적는다.

`Person` 은 이 프리셋의 8종에 없다. 이유와 나중에 추가하는 절차는
[[창업-객체타입]] 의 워크드 예시에 있다. 추가할 때 personal-rag 나 team-ops 가
같은 워크스페이스에 얹혀 있으면 그때 위 절차가 걸린다.

## 술어 어휘

프로퍼티가 아니라 관계다. frontmatter `links:` 맵 또는 본문 섹션의 위키링크로 쓴다.
`broader` / `related` / `subject` 는 코어 소관이니 객체 관계에 재사용하지 않는다.

### 주장과 근거

이 프리셋의 본체다. 나머지 절은 이 축을 받치는 보조다.

| 술어 | 방향 | 기수 | 의미 |
|---|---|---|---|
| claims | 제출문서 -> 가설 | 1:n | 이 문서가 주장하는 것 |
| claimedIn | 가설 -> 제출문서 | 1:n | 역방향 |
| supports | 근거 -> 가설 | n:n | 이 관측이 지지하는 주장 |
| refutes | 근거 -> 가설 | n:n | 이 관측이 반증하는 주장 |
| supportedBy | 가설 -> 근거 | 1:n | 역방향 |
| refutedBy | 가설 -> 근거 | 1:n | 역방향 |
| tests | 마일스톤 -> 가설 | n:n | 이 일이 시험하려는 주장 |
| testedBy | 가설 -> 마일스톤 | 1:n | 역방향 |
| assumes | 제공물 / 고객군 / 자금 -> 가설 | n:n | 이것이 딛고 선 전제 |
| cites | 제출문서 -> 근거 | 1:n | 이 문서가 근거로 든 것 |

`claims` 와 `claimedIn` 중 **정본은 `claims`, 즉 문서 쪽이다.** 문서는 제출하면 닫히고
그 안의 주장 목록은 그 시점에 고정된다. 가설은 오래 살면서 여러 문서에 계속 등장하므로,
가설 쪽에 적으면 문서를 낼 때마다 가설 노트를 전부 열어야 한다.

`supports` / `refutes` 와 그 역방향 중 **정본은 근거 쪽이다.** 가설은 먼저 서고 근거는
나중에 하나씩 붙는다. 근거 쪽에 적으면 새 관측 하나에 파일 하나만 만들면 끝난다.
가설 쪽에 적으면 관측이 들어올 때마다 가설 노트를 고쳐야 하고, 그 마찰이 정확히
근거 를 안 만들게 만드는 원인이다.

`tests` 와 `testedBy` 중 **정본은 `tests`, 즉 마일스톤 쪽이다.** 마일스톤은 끝나면 닫히고
가설은 계속 산다. `supports` 와 같은 논리다.

`assumes` 는 역방향을 두지 않는다. 가설 쪽에서 "나를 딛고 선 것들" 을 훑어야 할 때는
백링크 검색으로 충분하고, 슬롯을 만들면 반증 시점에 두 곳을 고쳐야 한다. 반증 후 살아
있는 `assumes` 를 찾는 조회는 [[창업-린트]] 규칙 17 에 있다.

`cites` 와 `claims` 를 혼동하지 않는다. `claims` 는 그 문서가 **주장한 것**이고 `cites`
는 그 주장을 받치려고 **끌어다 쓴 것**이다. 근거 없이 주장만 있는 문서를 찾는 조회가
이 둘의 차이에서 나온다.

### 제품과 고객

| 술어 | 방향 | 의미 |
|---|---|---|
| ownedBy | 제공물 / 고객군 / 가설 / 근거 / 마일스톤 / 자금 / 제출문서 -> 사업체 | 소속 사업체 |
| offers | 사업체 -> 제공물 | 역방향. 루트에서 훑을 때 |
| pursues | 사업체 -> 마일스톤 | 역방향 |
| holds | 사업체 -> 가설 | 역방향 |
| targets | 제공물 -> 고객군 | 이 제품이 겨냥하는 고객군 |
| servedBy | 고객군 -> 제공물 | 역방향 |
| describes | 제출문서 -> 제공물 / 고객군 | 이 문서가 설명하는 대상 |
| aboutSegment | 근거 -> 고객군 | 이 관측의 대상 고객군 |
| supersedes | 제공물 -> 제공물, 제출문서 -> 제출문서 | 이것이 대체한 것 |
| supersededBy | 같은 두 방향의 역 | 역방향 |

`ownedBy` 가 정본이다. `offers`, `pursues`, `holds` 는 루트 노트를 사람이 읽을 때의
편의 링크이고 갱신 의무가 없다.

**`ownedBy` 의 range 는 사업체 다.** 사람이나 고객사를 가리키면 규칙 12 위반이다. WS
하나에 사업체 인스턴스가 하나이므로 이 값은 사실상 상수이고, 상수를 굳이 적는 이유는
나중에 워크스페이스를 합칠 때 소속이 남아 있어야 하기 때문이다.

`targets` 와 `servedBy` 중 **정본은 `targets`, 즉 제품 쪽이다.** 고객군은 오래 살고
제품은 갈린다.

`supersedes` 와 `supersededBy` 중 **정본은 `supersedes` 쪽이다.** 새 판은 무엇을
대체하는지 알고 쓰이고, 옛 판은 자기가 언제 대체될지 모른다. 옛 쪽에는 `status` 를
`superseded` 또는 `retired` 로 바꾸는 것으로 충분하다.

### 자금과 제출

| 술어 | 방향 | 의미 |
|---|---|---|
| fundedBy | 마일스톤 -> 자금 | 이 일의 재원 |
| funds | 자금 -> 마일스톤 | 역방향 |
| requires | 자금 -> 제출문서 | 이 공고가 요구하는 제출물 |
| delivers | 마일스톤 -> 제공물 / 제출문서 | 이 일이 내놓는 것 |

`fundedBy` 와 `funds` 중 **정본은 `fundedBy`, 즉 마일스톤 쪽이다.** 지원사업 하나가
여러 마일스톤을 덮고 마일스톤은 계속 는다. 소비하는 쪽에 적는 원칙이다.

`requires` 는 제출물 체크리스트 자리다. 공고가 요구하는 서류 중 아직 제출문서 가 없는
것이 곧 할 일이고, 그 조회가 마감 직전에 값이 가장 크다.

### 보조 술어

의미가 자명해 별도 정의를 두지 않고 어휘에만 등재한다.

`sourceFile` (원본 파일 상대경로), `relatedObjects` / `relatedViews` (다용도 연결),
`references` (다용도 참조).

## 인터페이스 (추상 타입)

여러 타입이 공통으로 갖는 구조. 폴더를 만들지 않고 이 표로만 존재한다.

### HasIdentity

구현: 8종 전부. `name` 또는 `slug`(필수), `aliases`, `tags`, `description`.

### Temporal

구현: 사업체, 가설, 근거, 마일스톤, 자금, 제출문서.

| 요구 프로퍼티 | 필수 | 설명 |
|---|---|---|
| 시작 필드 |  | foundedAt / statedAt / collectedAt / startDate / announcedAt / authoredAt |
| 종료 필드 |  | settledAt / doneAt / decidedAt |

**시작 필드에 O 를 걸지 않는다.** 창업 초기 자료는 시작 시점이 자주 비어 있고, 창업일을
언제로 잡을지조차 정하지 않은 경우가 흔해서 필수로 걸면 지어낸 날짜가 들어온다. 필수
여부는 타입별 프로퍼티 표([[창업-객체타입]])를 따르고, Temporal 이 요구하는 것은
시작 필드가 그 타입의 스키마에 존재한다는 것까지다.

그래서 시작 필드 중 O 로 남는 것은 가설 의 `statedAt` 과 근거 의 `collectedAt`
둘뿐인데, 그 둘은 Temporal 때문이 아니라 규칙 13 과 15 가 각각 요구해서 그렇다.

제공물 과 고객군 는 Temporal 이 아니다. 둘 다 `status` enum 이 시간축 역할을 하고,
언제 생각났는지가 조회에 쓰이지 않는다.

### Owned

구현: 사업체 를 뺀 7종. 소속 사업체가 반드시 있는 것.

| 요구 프로퍼티 | 필수 | 설명 |
|---|---|---|
| `ownedBy` 링크 | O | **사업체 참조.** 사람이나 기관이면 위반 |

### Falsifiable

구현: 가설 하나. 이 프리셋 고유 인터페이스다.

| 요구 프로퍼티 | 필수 | 설명 |
|---|---|---|
| `falsifiable` | O | 무엇이 관측되면 틀린 것인가 |
| `status` | O | 검증 상태 |

타입 하나짜리 인터페이스를 두는 이유는 나중에 늘어나기 때문이다. 경쟁 가정, 규제 가정,
기술 가정을 별도 타입으로 뺄 때 이 인터페이스를 구현하게 하면 반증 조건 요구가 자동으로
따라간다.

### Sourced

구현: 근거, 제출문서. 밖에서 온 것이거나 밖으로 나간 것.

| 요구 프로퍼티 | 필수 | 설명 |
|---|---|---|
| `sources` 또는 `source` 또는 `sourceFile` | 권장 | 원본이 어디 있는가 |

**인터페이스가 필수를 요구하지 않는 유일한 자리다.** 출처의 필요가 타입이 아니라 `kind`
에 달려 있기 때문이다. 인터뷰는 `method` 로 충분하고 md 로 직접 쓴 원페이저에는 가리킬
원본 파일이 없다. 셋 중 하나를 일괄 O 로 걸면 빈 칸을 채우려고 아무 값이나 들어가고,
그렇게 들어온 값이 다음에 출처로 읽힌다.

대신 둘로 나눠 받는다. `kind: desk` 인 근거 는 `source` 가 필수이고 그 규정은
[[창업-객체타입]] 의 근거 절에 있다. 나머지는 규칙 16 이 규율 검사로 덮는다.

## 값 타입

### 가설Status

- `unvalidated` 미검증 - 주장만 있고 관측이 없다. **기본값이다**
- `testing` 검증 중 - 시험할 마일스톤이 걸려 있다
- `validated` 지지됨 - `supports` 로 걸린 근거 가 있다(규칙 14)
- `invalidated` 반증됨 - `refutes` 로 걸린 근거 가 있다
- `retired` 폐기 - 틀린 것이 아니라 더는 묻지 않게 된 것

**`unvalidated` 가 부끄러운 상태가 아니다.** 창업 초기 가설의 대부분이 여기 있는 것이
정상이고, 그것을 숨기려고 `validated` 로 올리는 순간 이 워크스페이스가 사업계획서와
같아진다. `validated` 는 근거가 있을 때만 쓴다.

`invalidated` 와 `retired` 를 구분하는 이유는 다음 사람이 읽을 때 뜻이 완전히 다르기
때문이다. 전자는 세상이 우리 생각과 달랐던 것이고 후자는 그 질문 자체가 무의미해진
것이다.

### Confidence

가설 전용. `hunch` / `indicative` / `strong`.

근거의 세기이지 확신의 세기가 아니다. hunch 는 근거 없음, indicative 는 소수 관측,
strong 은 반복 관측이다. 경계값은 프리셋이 정하지 않는다. 대상 워크스페이스가 자기
기준을 제출문서 나 개념 노트에 적고 거기를 가리킨다.

### 자금Status

`watching` / `preparing` / `applied` / `selected` / `rejected` / `contracted` / `closed`.

`selected` 와 `contracted` 를 나눈 이유는 그 사이에 협약이라는 절차가 있고 거기서
조건이 바뀌기 때문이다. 선정 금액과 협약 금액이 다른 경우가 흔하다.

## 공유 프로퍼티

| 이름 | 타입 | 사용 | 설명 |
|---|---|---|---|
| `tags` | string[] | 전체 | 자유 분류 |
| `description` | text | 전체 | 짧은 설명 |
| `updated` | date | 전체 | 마지막 갱신 (GUIDE §6 이 bump) |
| `sources` | url[] | 전체 | 출처와 근거 |
| `status` | enum | 사업체 를 뺀 7종 | 타입별 enum |

`sources` 가 이 프리셋에서 장식이 아니다. 규칙 16 이 이 칸을 근거로 돈다.

## 무결성 규칙 추가

코어 lint 규칙 1~6 에 더한다. 점검 방법은 [[창업-린트]].

7. 객체 인스턴스의 `type:` 은 허용 노트 타입에 등재된 값이어야 한다.
8. 객체 인스턴스는 필수 프로퍼티(PK, 각 타입의 O 표시), 그리고 Owned 구현 타입은
   `ownedBy` 링크를 갖는다.
9. `links:` 와 본문의 모든 위키링크는 실재하는 노트를 가리킨다.
10. 술어는 이 문서의 어휘에 있는 것만 쓴다.
11. 정방향과 역방향 술어를 같은 사실에 대해 양쪽 노트에 동시에 적지 않는다. 정본 방향은
    아래 표가 정본이다.

| 쌍 | 정본 (여기 적는다) | 비정본 |
|---|---|---|
| 주장 | 제출문서 의 `claims` | 가설 의 `claimedIn` |
| 지지 | 근거 의 `supports` | 가설 의 `supportedBy` |
| 반증 | 근거 의 `refutes` | 가설 의 `refutedBy` |
| 시험 | 마일스톤 의 `tests` | 가설 의 `testedBy` |
| 소유 | 각 객체의 `ownedBy` | 사업체 의 `offers` / `pursues` / `holds` |
| 겨냥 | 제공물 의 `targets` | 고객군 의 `servedBy` |
| 재원 | 마일스톤 의 `fundedBy` | 자금 의 `funds` |
| 판본 | 새 노트의 `supersedes` | 옛 노트의 `supersededBy` |

**정본이 전부 "나중에 생기는 쪽" 에 있는 것에 주의한다.** 기준은 새 사실이 들어올 때
고치는 파일 수이고, 이 프리셋에서는 근거와 문서가 계속 늘고 가설과 고객군은 오래
버틴다. 비정본 쪽은 사람이 읽을 때의 편의 링크이고 갱신 의무가 없다. 템플릿은 정본
슬롯만 제공한다.

12. 객체 인스턴스는 `broader` 를 갖지 않는다. `ownedBy` 의 대상은 사업체 다.

여기까지는 다른 두 프리셋과 같다. 아래 여섯이 이 프리셋 고유다.

13. **가설 는 `falsifiable` 을 갖는다.** 무엇이 관측되면 틀린 것인지 못 적는
    문장은 가설이 아니라 구호다. 이 칸이 비면 그 노트는 반증될 수 없고, 반증될 수 없는
    것이 폴더에 쌓이면 검증 상태 조회가 통째로 무의미해진다.
14. **`status: validated` 인 가설 는 `supports` 로 걸린 근거 를 하나 이상
    갖는다.** 근거 없는 검증 표시가 이 워크스페이스에서 가장 비싼 거짓말이다. 그 표시를
    보고 다음 문서가 그 주장을 사실로 쓴다.
15. **근거 는 `collectedAt` 과 `sampleSize` 를 갖는다.** 시점과 규모 없는 관측은
    관측이 아니라 인상이다. 읽는 사람은 규모를 늘 큰 쪽으로 추정한다.
16. **숫자에는 출처가 붙는다.** 본문에 시장 규모, 목표 매출, 단가, 성장률 같은 정량
    주장이 나오는데 `sources` 가 비어 있으면 위반이다. 규율 검사다.
17. **반증된 가설 위에 산 것이 남아 있지 않다.** `status: invalidated` 인 가설 에
    `assumes` 로 걸린 제공물 / 고객군 / 자금 중 아직 활성 상태인 것이 있으면
    경고다. 규율 검사다.
18. **`submittedTo` 가 있는 제출문서 는 `submittedAt` 과 `version` 을 갖는다.** 어디에
    언제 어느 판을 냈는지가 같이 있어야 중복 수혜 판정과 재신청 판정이 선다.

16 과 17 은 구조 검사가 아니라 규율 검사다. 의도한 것이다. 이 프리셋이 실패하는 방식은
스키마 위반이 아니라 **출처 없는 숫자와 반증 후에도 살아남는 전제**이고, lint 가 그것을
세지 않으면 아무도 세지 않는다.
