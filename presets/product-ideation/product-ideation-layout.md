# 레이아웃

프로젝트급 개념 하나가 대상 워크스페이스에서 갖는 폴더 모양, 이름 규칙, 분류 규칙이다.
코어 `_context-protocol/_ontology.md` "쓰기 전에 분해한다" 의 뼈대를 구체화한다.

## 트리

`<상위>` 는 대상 워크스페이스의 프로젝트 묶음 개념이다(팀 프루퍼는 `프로젝트/`, 개념
`[[projects]]`). 없으면 top concept 아래에 바로 둔다.

```
<상위>/
  <프로젝트>/
    <프로젝트>.md              개념 노트 (project.md.tpl)
    결정이력.md                (decision-log.md.tpl)
    용어.md                    (glossary.md.tpl)
    <종류>_<YYYYMMDD>.md       원 기록, 있을 때만 (raw-record.md.tpl)
    <축A>/
      <slug>-<축A-id>.md       축 개념 노트 (axis.md.tpl)
      <측면>/
        <slug>-<측면-id>.md    측면 개념 노트 (aspect.md.tpl)
        <주제>.md              주제 문서 (topic.md.tpl)
    <축B>/
      ...
```

타이니어스에 대입하면 이렇다.

```
프로젝트/타이니어스/
  타이니어스.md  결정이력.md  용어.md  아이디에이션_20260924.md  기술선택_20260924.html
  사업/tinyus-business.md
    고객/tinyus-customer.md  타깃과가치.md
    과금/tinyus-revenue.md   과금모델.md
    브랜드/tinyus-brand.md   이름과도메인.md
  서비스/tinyus-service.md
    경험/tinyus-experience.md  화면구성.md  감정과상태.md  공간.md
    캐릭터/tinyus-character.md 캐릭터체계.md  뼈대와렌더링.md
    아키텍처/tinyus-architecture.md  인프라와스택.md  앱스택.md  로컬개발과큐.md
```

## 이름 규칙

- 폴더 이름과 주제 문서 이름은 워크스페이스 언어로 쓴다. 사람이 트리를 보고 읽는 층이다.
- 개념 id(개념 노트 파일명)는 짧은 영문 slug 에 축이나 측면 이름을 붙인다(`tinyus-customer`).
  위키링크가 파일명으로 해석되므로 워크스페이스 전체에서 유일해야 한다. `customer` 처럼
  맨 이름을 쓰면 두 번째 프로젝트에서 충돌한다.
- 프로젝트 개념 노트만은 폴더 이름과 같은 이름을 쓴다(`타이니어스/타이니어스.md`).
  프로젝트 이름으로 부르는 위키링크 `[[타이니어스]]` 가 그대로 해석된다.
- 루트 공통 문서는 워크스페이스 언어의 고정 이름을 쓴다. 한국어는 `결정이력.md`,
  `용어.md`, 영문은 `decision-log.md`, `glossary.md`. lint 는 두 표기를 다 찾는다.
- 루트 공통 문서와 주제 문서는 위키링크 대상으로 쓰지 않는다. 두 프로젝트가 모두
  `결정이력.md` 를 가져도 되고, 가리킬 때는 상대경로나 그 프로젝트의 개념 노트 링크를 쓴다.
  이름이 전역에서 유일해야 하는 것은 개념 id 뿐이다.
- 이름이 정해지기 전에는 가칭 폴더와 slug 로 시작한다. 같은 세션 안의 이름 변경은 생성의
  연장이라 승인 없이 한다(코어 "태어날 때 분해한다").
- 원 기록은 `<종류>_<YYYYMMDD>.md`(예: `아이디에이션_20260924.md`). 날짜가 이름에 들어가야
  같은 종류의 두 번째 대화가 앞의 것을 덮지 않는다.

## 축 고르기

축은 측면들을 성격으로 가르는 첫 분기다. 둘이 기본이고 셋까지 둔다. 넷 이상이면 측면을
축으로 세우고 있을 가능성이 크다.

| 도메인 | 축 | 경계 문장 |
|---|---|---|
| 제품, 서비스, 사업 아이디어 | 사업 / 서비스 | 값을 정당화하면 사업, 만드는 방법을 정하면 서비스 |
| 콘텐츠, 교육 | 기획 / 제작 | 누구에게 무엇을 왜 전하는지 정하면 기획, 어떻게 만들어 내보내는지 정하면 제작 |
| 연구, 탐색 | 질문 / 방법 | 무엇을 알아내려는지 정하면 질문, 어떻게 알아내는지 정하면 방법 |
| 내부 도구 | 문제 / 해법 | 누가 무엇 때문에 불편한지 정하면 문제, 무엇을 만들어 푸는지 정하면 해법 |

표에 없는 도메인은 새로 고른다. 조건은 경계 문장 한 줄로 두 축을 가를 수 있어야 한다는
것이다. 그 문장이 안 써지면 표의 첫 행(사업 / 서비스)으로 시작한다. 어느 축에도 안 맞는
측면이 쌓이면 축을 다시 고른다. 기존 파일이 움직이므로 그때는 매핑 승인을 거친다.

## 측면 목록 (사업 / 서비스 축의 흔한 측면)

| 축 | 측면 | 한 줄 정의 |
|---|---|---|
| 사업 | 고객 | 누구에게 파는가, 그들이 사는 가치, 성장 경로 |
| 사업 | 과금 | 무엇에 돈을 받는가, 소유 규칙, 과금 관련 규제 |
| 사업 | 브랜드 | 이름, 도메인, 상표, 톤 |
| 사업 | 시장 | 경쟁과 대체재, 시장 크기와 그 출처 |
| 사업 | 운영 | 지원, 정책, 신뢰와 안전, 법무 |
| 서비스 | 경험 | 화면 구성, 흐름, 상호작용, 상태 |
| 서비스 | 도메인 모델 | 서비스 고유 개체와 규칙(타이니어스의 캐릭터) |
| 서비스 | 아키텍처 | 인프라, 스택, 데이터, 개발 환경 |

목록은 출발점이다. 대화에 나온 측면만 만들고 빈 측면 폴더를 미리 만들지 않는다. 비어
있게 될 폴더는 만들지 않는다는 코어 원칙과 같다.

## 분류 규칙

- 한 문장이 두 측면에 걸치면 결정이 난 쪽에 둔다. "슬롯 무료 2개" 는 캐릭터 체계에도
  닿지만 값을 정하는 결정이라 과금이다. 다른 쪽 문서에는 위키링크로 가리킨다.
- 여러 측면에 걸친 결정은 결정이력에 한 줄 두고 각 측면 문서에서 그 결정을 인용한다.
- 비-md 산출물(HTML 비교표, 이미지, 스프레드시트)은 그것이 다루는 측면 폴더에 둔다.
  여러 측면을 다루면 프로젝트 루트에 두고 개념 노트의 구조 표에 한 줄 적는다.
- 프로젝트 개념 노트의 "현재 단계" 절은 날짜를 붙여 덮어쓴다. 단계 변화 이력은
  action-log 가 든다. 다음에 할 일 같은 진행 중 작업 상태는 `memory/` 로 간다.
- 측면 개념 노트는 정의와 문서 목록만 든다. 본문은 주제 문서로 간다.
