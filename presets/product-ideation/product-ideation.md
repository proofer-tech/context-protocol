# 제품 아이디에이션 프리셋 (폴더 개념)

이 노트는 `presets/product-ideation/` 폴더의 개념 노트다. 폴더 중첩이 broader 를
뜻하니 이 프리셋은 [[preset-library]] 아래에 있다. 이 폴더의 파일은 전부 설계
문서이고, 여기에 실제 프로젝트 인스턴스를 만들지 않는다.

## 무엇을 위한 프리셋인가

새 프로젝트나 아이디어가 대화로 커질 때 에이전트는 규칙을 다 지키고도 결과를 개념
노트 한 장과 큰 문서 한두 장으로 끝내곤 했다. 무결성 lint 는 통과하지만 주제별로 나뉘어
있지 않아서, 사용자가 지적한 뒤에야 재편했다. 팀 프루퍼 워크스페이스에서 두 번 실측됐다.

- 프루퍼 플랫폼: 컨셉기획 v0.1~v0.4 단일 기획서로 쌓이다가 2026-09-09 에 사업과 서비스
  두 축, 축마다 하위 개념 다섯, 루트 공통 문서(개요, 결정이력, 리스크대장, 용어, 출처)로
  재편했다.
- 타이니어스: 2026-09-24 아이디에이션 대화 한 번 동안 개념 노트 1장, 아이디에이션 문서
  1장, HTML 1장으로 쌓였다. 다음 날 사용자 지적 뒤 개념 9개, 문서 13개로 분해했다.

두 사례 모두 재편 후의 모습이 정답이고, 이 프리셋의 템플릿은 그 모양을 옮긴 것이다.
비교 기준은 팀 프루퍼의 `프로젝트/타이니어스/` 다.

## 코어 규칙과 나눠 갖는 것

분해 규칙 자체는 코어에 있다. `_context-protocol/_ontology.md` 의 "쓰기 전에 분해한다"
가 한 파일 한 주제, 쓰기 전 측면 판정, 태어날 때 분해, 프로젝트급 개념의 뼈대, 원
기록 표식, 내용 기준 분할 신호를 정하고, `_schema/concept-scheme.md` 의 "본문 절 규약"
이 확정과 제안을 가른다. 그래서 사용자가 이 프리셋 이름을 부르지 않아도 뼈대는 선다.

이 프리셋은 그 규칙을 쓰기 쉽게 만드는 도구를 더한다.

| 파일 | 역할 |
|---|---|
| [[product-ideation-layout]] | 대상 트리, 이름 규칙, 축 고르기, 측면 목록, 분류 규칙 |
| [[product-ideation-apply]] | 적용 절차. 빈 개념에서 시작할 때와 이미 뭉친 문서를 분해할 때 |
| [[product-ideation-intake]] | 대화나 원 기록에서 측면과 출처를 뽑아 첫 인스턴스를 심는 절차 |
| [[product-ideation-lint]] | 프로젝트 폴더 하나를 헤드리스로 점검하는 목록과 스크립트, 수용 시험 |
| `templates/` | 프로젝트, 축, 측면, 주제, 결정이력, 용어, 원 기록 템플릿 7종 |

다른 프리셋(personal-rag, team-ops, compliance, startup)은 워크스페이스 전체의 타입
어휘를 정한다. 이 프리셋은 워크스페이스 안의 개념 하나에 얹힌다. 새 노트 타입과 새
술어가 없고, 코어 어휘(concept, document, `canon_note`, 본문 절 규약)만 쓴다. 그래서
적용 절차에 스킴 병합 단계가 없다.

## 자동 트리거를 두지 않은 이유

요청은 사용자가 프리셋 이름을 부르지 않아도 새 프로젝트급 개념을 만들 때 이 프리셋을
적용하는 트리거를 검토해 달라는 것이었다. 두지 않기로 했다.

- 프리셋 호출 계약은 이름 호출에 묶여 있다. 자동 적용은 계약의 둘째 단계(프로토콜
  설치와 MIGRATE)를 새 프로젝트마다 끌고 온다.
- 대상 워크스페이스에서 이 폴더에 닿는 길(cross-project import)이 세션마다 보장되지
  않는다. 닿을 때만 켜지는 트리거는 닿지 못한 세션에서 조용히 꺼지고, 그 조용한 실패가
  이번에 고치려는 실패와 같은 모양이다.
- 뼈대 생성을 코어에 두면 프리셋 없이도 수용 기준을 만족한다.

대신 코어 규칙이 이 폴더의 템플릿을 참조 모양으로 가리킨다. 닿으면 템플릿을 읽어 쓰고,
닿지 않으면 코어 절만으로 만든다. 템플릿을 읽는 것은 프리셋 적용으로 치지 않는다.
사용자가 "product-ideation 프리셋으로" 라고 부르면 그때 호출 계약 4단계가 돈다.

## 창업 프리셋과의 경계

[[startup]] 은 워크스페이스가 곧 사업체일 때 쓴다. 이 프리셋은 기존 워크스페이스 안에서
아이디어가 태어날 때 쓴다. 아이디어가 법인이나 독립 워크스페이스로 떨어져 나가면 창업
프리셋으로 옮겨 가는 것이 자연스럽다.

옮길 때 한 가지를 조심한다. 이 프리셋의 "확정" 은 사용자가 정했다는 뜻이고 검증됐다는
뜻은 담지 않는다. "직장인 커플이 이어짐의 가치를 산다" 가 확정 절에 있어도 그것은 결정된
방향이지 확인된 사실은 아니다. 창업 프리셋으로 옮길 때 확정 절의 가치 주장은 가설로 옮겨
적고 반증 조건을 붙인다.

## 설치하는 것

대상 워크스페이스에는 파일을 설치하지 않는다. 적용은 프로젝트 인스턴스를 만드는 일이다.
템플릿을 대상 워크스페이스로 복사할지는 [[product-ideation-apply]] Step 0 에서 정한다.

## 수용 기준

새 세션에서 빈 개념으로 시작해 사업 아이디어 대화를 15턴쯤 나눈다. 대화에는 고객,
과금, 화면 경험, 기술 선택, 이름이 섞여 나온다. 사용자는 구조로 정리해 달라고 따로
말하지 않는다. 대화가 끝났을 때 아래가 모두 참이면 통과다. 점검 방법은
[[product-ideation-lint]].

1. 축이 2개 이상 있고, 축마다 하위 개념 폴더와 주제별 문서가 있다.
2. 루트에 결정이력(번복 포함)과 용어가 있다.
3. 200줄을 넘는 문서가 없고, 한 문서가 여러 주제를 품고 있지 않다.
4. 문서마다 확정과 제안이 갈라져 있다.
5. 원 대화 기록이 있다면 원 기록으로 표시돼 있다.
6. integrity-lint 통과, MEMORY 인덱스와 `_project.md` 갱신, action-log 기록.
