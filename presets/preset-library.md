# 프리셋 라이브러리 (폴더 개념)

이 노트는 `presets/` 폴더의 개념 노트다. 즉 `presets/` 폴더 = 개념 preset-library.
이 폴더 안의 파일과 하위 프리셋 폴더는 위치만으로 이 개념에 속한다.

## 왜 분리하나

CONTEXT_GUIDE.md 는 어떤 주제의 워크스페이스에도 공통으로 적용되는 규범이다
(레이어, 조회/쓰기 프로토콜, 마운트 함정, 구조 우선 온톨로지). 반면 "무엇을 객체로
볼 것인가"는 주제마다 다르다. 사람과 관계를 다루는 워크스페이스와 법령을 다루는
워크스페이스는 같은 프로토콜을 쓰지만 타입 어휘가 완전히 다르다.

그 주제별 부분만 떼어 프리셋으로 둔다. 프로토콜은 하나, 프리셋은 여러 개.

## 수록 프리셋

- [[personal-rag]] - 한 사람을 디지털 트윈으로 표현하는 개인 지식그래프.
  출처 계보: `hsol-info-blob/vault` (Palantir Foundry OMS 모델 참조).
  용도별 사전 설정 3종은 [[personal-rag-variants]].

- [[compliance]] - 외부 법령을 사내 규정과 통제로 내려받아 이행 증거까지 추적한다.
  타입 8종(Statute, Regulation, Obligation, Control, Evidence, Audit, Finding, Unit).
  책임 주체가 사람이 아니라 조직 단위인 것이 이 프리셋의 전제다.

- [[team-ops]] - 한 팀이 어떻게 일하는지를 여러 사람이 함께 쌓는 운영 지식그래프.
  타입 8종(Team, Person, Initiative, Decision, Practice, System, Incident, Metric).
  [[personal-rag]] 의 1인 루트 가정이 깨지는 자리를 메운다. 중심 타입은 Decision 이다.

- [[startup]] - 예비창업자와 초기창업기업이 자기 사업 자료를 검증 상태가 드러나는
  지식그래프로 세운다. 타입 8종(사업체, 제공물, 고객군, 가설, 근거, 마일스톤, 자금,
  제출문서). 중심 타입은 가설 이고, 논지는 사업계획서가 주장과 사실을 같은 문장으로
  적는다는 것이다. 사람을 타입으로 일부러 넣지 않았고 그것이 필요해지는 시점이
  [[team-ops]] 로 옮길 시점이다. **타입명만 한글이다.** 2026-09-16 에 프리셋 전체를
  한글로 옮겼다가, 2026-11-24 에 프리셋 id 와 폴더명, 파일명을 다른 프리셋처럼 영문
  `startup` 으로 되돌렸다. 타입명(사업체, 가설 등)은 한글 그대로이고 YAML 키와 술어와
  enum 값은 영문이다. 예전 이름: `창업` (이 이름으로 불러도 이 프리셋으로 받는다).
  조회 규칙과 매핑 줄은 [[startup-lookup]].

- [[product-ideation]] - 워크스페이스 안에서 프로젝트급 개념(프로젝트, 제품, 사업 아이디어)이
  대화로 자랄 때 처음부터 축과 측면으로 분해된 구조에 쌓이게 한다. 다른 넷과 달리 워크스페이스
  전체의 타입 어휘를 정하지 않고 개념 하나에 얹히며, 새 타입과 새 술어가 없다. 분해 규칙
  자체는 코어(`_context-protocol/_ontology.md` "쓰기 전에 분해한다")에 있고 이 프리셋은 그
  뼈대의 템플릿, 대화에서 측면을 뽑는 인테이크, 헤드리스 점검을 묶는다. 이름을 부르지 않으면
  자동 적용하지 않는다. 코어 규칙이 템플릿을 참조 모양으로 가리킬 뿐이다. 2026-09-25 신설.

## 프리셋 한 벌의 구성

프리셋 폴더 `presets/<preset-id>/` 는 다음을 갖춘다. 이름은 `<preset-id>-*` 접두로
맞춰 grep 한 번에 프리셋 전체가 잡히게 한다.

| 파일 | 역할 |
|---|---|
| `<preset-id>.md` | 프리셋의 개념 노트. 무엇을 위한 프리셋인가, 무엇을 설치하는가, 원본 대비 편차 |
| `<preset-id>-layout.md` | 대상 워크스페이스에 만들어질 폴더/파일 구조와 분류 규칙 |
| `<preset-id>-object-types.md` | 타입별 프로퍼티 표, PK, 구현 인터페이스, 허용 출력 링크 |
| `<preset-id>-schema.md` | concept-scheme 확장: 허용 노트 타입, 술어 어휘, 값 타입, 공유 프로퍼티, 무결성 규칙 |
| `<preset-id>-actions.md` | 액션 타입 어휘와 action-log 엔트리 형식 |
| `<preset-id>-apply.md` | 적용 절차 (신규/기존 워크스페이스, 마운트 제약 대응, 검증) |
| `<preset-id>-intake.md` | 초기 문답 질문지. AskUserQuestion 라운드 대본, 답변->파일 매핑, 중단/재개 |
| `<preset-id>-variants.md` | (선택) 용도별 사전 설정. 타입/술어를 갈라놓지 않고 주축, 조회 규칙, 인테이크 순서만 분기 |
| `<preset-id>-조회규칙.md` | (선택) 대상 WS `CONTEXT.md` 에 얹는 조회 규칙 절과 매핑 줄 형식. 변형이 없는 프리셋은 여기 둔다 |
| `<preset-id>-lint.md` | 헤드리스 무결성 점검과 조회 레시피 |
| `templates/` | 인스턴스 생성용 템플릿 |

인테이크가 필요한 이유는 프리셋 공통이다. 적용이 끝나면 구조는 서지만 인스턴스는 비어 있고,
GUIDE §12 능동적 축적은 대화가 일어나야 작동한다. 프리셋 파일만 받은 사람에게는 그 대화
이력이 없으므로 부트스트랩 구간이 빈다. 인테이크는 그 구간만 메우는 문서이고, 사용자가 무엇을
적어야 하는지 모른다는 것을 전제로 **선택지로 묻는다**. 채울 인스턴스가 없는 프리셋
(예: 규칙집 성격)에는 두지 않아도 된다.

## 새 프리셋 추가 규칙

1. `presets/<preset-id>/` 폴더를 만들고 그 안에 `<preset-id>.md` 개념 노트를 둔다.
   폴더 중첩이 broader 를 뜻하므로 `broader: "[[preset-library]]"` 를 적는다.
2. 위 구성표의 파일을 채운다. 최소 요구는 개념 노트 + layout + apply 셋이다.
3. 프리셋은 **대상 워크스페이스를 서술**할 뿐, 이 워크스페이스에 객체를 만들지
   않는다. 프리셋 폴더 안의 파일은 전부 설계 문서다.
4. 이 노트의 "수록 프리셋" 목록에 한 줄 추가하고, `memory/MEMORY.md` 에 인덱스
   한 줄을 추가한다.
5. 프리셋이 concept-scheme 을 확장하면 그 확장은 프리셋 안에서만 정의한다. 코어
   `_context-protocol/_schema/concept-scheme.md` 는 건드리지 않는다. 대상
   워크스페이스가 프리셋을 적용할 때 자기 스킴에 확장을 병합한다.

## 프리셋 vs 프로토콜 경계

프리셋에 넣는 것: 객체 타입, 술어(링크 타입), 값 타입, 인스턴스 폴더 모양, 템플릿,
그 주제 특유의 조회 레시피.

프리셋에 넣지 않는 것: 조회 프로토콜, 쓰기 프로토콜, 마운트 함정 대응, Desktop
Commander 표준, action-log 의 시간축 규칙, 능동적 축적 트리거. 이것들은 전부 GUIDE
소관이고 프리셋은 참조만 한다. 프리셋이 프로토콜 규칙을 재정의하려 들면 두 정본이
갈라져 드리프트가 생긴다.

## 프로토콜을 어떻게 참조하나 (버전 결합 금지)

프리셋 문서는 프로토콜을 **버전 번호나 지침 항목 번호로 가리키지 않는다.** 규칙을
이름으로 부른다. "능동적 구조 생성 원칙", "메모리 라우팅 규칙", "민감정보 규칙"처럼.

이유는 두 겹이다. 첫째, 버전 번호는 오른다. "4.7 절차대로"라고 적힌 문장은 5.0 에서
읽는 사람에게 아무 말도 하지 않는다. 둘째, **지침 항목 번호는 5.0 에서 사라졌다.**
지침은 이제 진입 정본으로 가는 3항목 부트스트랩이고 규칙은 그 정본에 산다(8.0 부터
CONTEXT.md, 그 전에는 CLAUDE.md). 그런데 정본의 번호 체계는 워크스페이스마다 다르다. 어느 워크스페이스는 항목 7 이
쓰기 프로토콜이고 다른 곳은 §9 다. 프리셋은 어느 워크스페이스에 얹혀도 성립해야 하므로
특정 워크스페이스의 번호를 알 수 없다.

GUIDE 의 절 번호(§4.5, §6, §10, §12)는 예외로 써도 된다. 가이드는 워크스페이스마다
같은 파일이고 절 번호가 안정적이다. 바뀌는 것은 지침 쪽 번호다.

## 프리셋 호출 계약

트리거는 사용자가 프리셋 이름을 대며 일을 시킬 때다. "<프리셋> 프리셋 사용해서
~해줘", "<프리셋> 프리셋으로 마이그레이션해줘", 또는 프리셋 이름과 함께 구조를
잡아달라는 요청. 이때 4단계를 이 순서로 밟는다. 뒤바꾸지 않는다.

1. **프리셋을 찾는다.** 위 "수록 프리셋" 목록에서 이름을 확인한다. 프리셋은 프로토콜
   워크스페이스의 `presets/` 에 산다. 다른 워크스페이스에서 호출됐으면 cross-project
   import(GUIDE §11)로 그 워크스페이스를 발견해 읽거나 직접 경로로 읽는다. 못 찾으면
   여기서 멈추고 되묻는다. 이름이 비슷한 다른 프리셋을 대신 적용하지 않는다.
2. **프로토콜을 먼저 설치한다.** 대상 폴더에 프로토콜이 있는지 확인해서, 없으면
   `CONTEXT_SETUP.md`, 있으면 `CONTEXT_MIGRATE.md` 로 LATEST_VERSION 까지
   맞춘다. 프리셋은 `_schema/concept-scheme.md`, `memory/`, `action-log/`, `_project.md`
   에 기대어 성립한다. 순서가 뒤바뀌면 기댈 것이 없는 상태에서 폴더만 생긴다.
3. **프리셋을 얹는다.** `<preset-id>-apply.md` 절차대로 폴더, 개념 노트, 스킴 확장,
   템플릿을 만든다. 여기까지는 파괴적이지 않으므로 승인을 기다리지 않는다(프로토콜의
   능동적 구조 생성 원칙: 생성은 되돌릴 것이 없다).
   프리셋에 `<preset-id>-intake.md` 가 있으면 이 단계 끝에서 그 질문지를 돌려 초기
   인스턴스를 채운다. 구조만 서고 비어 있는 워크스페이스는 조회가 성립하지 않는다.
4. **기존 파일을 정리한다.** 아래 정책을 따른다. 이 단계만 성질이 다르다.

빈 폴더에 프리셋을 얹는 경우 4단계는 없다. 그때는 3단계의 인테이크가 사실상 마지막 작업이다.

### 기존 파일 정리 정책

폴더 생성과 파일 이동은 되돌리기 난이도가 다르다. 생성은 되돌릴 것이 없다. 이동은
잘못되면 위치가 곧 분류라서 조용한 오분류가 되고, 마크다운 상대링크와 비-md 참조가
깨진다(위키링크는 파일명으로 해석돼 살아남는다). 그래서 **생성은 승인 없이, 이동은
매핑 승인 후**로 갈라 둔다.

1. 3단계까지 먼저 끝낸다. 구조가 있어야 어디로 갈지 말할 수 있다.
2. 대상 폴더를 인벤토리하고 "이 파일 -> 이 타입 폴더" 매핑표를 만든다. 각 행에 근거를
   한 줄 적는다. 근거를 못 적는 파일은 매핑이 아니라 질문 대상이다.
3. 매핑표를 제시한다. 파일명과 내용이 타입을 자명하게 지시하는 것은 "바로 이동"으로,
   애매한 것은 "확인 필요"로 나눠 보여준다. 전자까지 일일이 묻지 않는다.
4. 승인 후 이동한다. 하네스의 호스트 파일 도구로 옮긴다(Cowork 에서는 Desktop Commander
   `move_file`). (proxy_mount: yes) 샌드박스 마운트는 이동의 unlink 절반을 거부한다(GUIDE §4.5).
5. 이동 후 참조를 고친다. 그 파일을 가리키던 마크다운 상대링크, `memory/MEMORY.md`
   인덱스 경로, `_project.md` 진입점을 갱신한다. 이 단계를 빼면 링크가 조용히 깨진다.
6. action-log 에 이동 내역을 남긴다. 무엇을 어디서 어디로, 왜. 오분류를 나중에
   되짚을 수 있는 유일한 기록이다.

### 어떤 타입에도 안 맞는 파일

가까운 타입에 밀어넣지 않는다. 프로토콜의 능동적 구조 생성 절차대로 새 타입 폴더를
만든다(구조 생성 + 어휘 확장, `_context-protocol/_ontology.md`). 프리셋의 타입 목록은 출발점이지 울타리가 아니다.

보류 폴더(`_inbox` 같은 것)를 만들어 미루지 않는다. 그 폴더는 개념이 아니라서 lint
예외가 필요하고, 예외가 한번 생기면 미분류 파일이 거기 영구히 남는다. 미루는 비용이
안 보이는 형태로 쌓이는 것이 보류 폴더의 문제다.

판단이 어렵다는 느낌 자체가 새 타입이라는 신호다.
