# 대상 워크스페이스 레이아웃

이 프리셋을 적용한 워크스페이스(이하 WS)가 갖는 구조다. 프로토콜 부속물은 6.0 부터
모든 워크스페이스에서 같은 이름 `_context-protocol/` 에 모인다.

## 분류가 성립하는 방식

1. **위치(1순위)**: `objects/가설/` 안의 md 는 개념 가설 소속이다.
   frontmatter 에 `subject` 를 적지 않아도 된다. 파일을 다른 타입 폴더로 옮기면 그것이
   재분류다.
2. **폴더 중첩 = broader**: `objects/가설/` 가 `objects/` 안에 있으므로
   가설 의 broader 는 venture-knowledge 다. 개념 노트 frontmatter 에 명시한다.
3. **frontmatter**: 한 인스턴스가 두 타입에 걸치는 예외적 경우에만 `subject` 로 다중
   소속을 적는다. 기본은 위치 하나로 끝낸다.
4. **비-md**: 사업계획서 원본 hwp 와 pdf, IR 슬라이드, 로고 파일, 인터뷰 녹취는 메타를
   붙이지 않는다. 관련 객체의 서브폴더에 두고 인덱스 노트에서 위키링크로 언급한다.

## 타입 폴더 = 개념 노트가 겸하는 두 역할

`objects/가설/가설.md` 한 파일이 (a) 폴더 가설 의 개념 노트이고
동시에 (b) 가설 객체 타입의 정의(프로퍼티 표, PK, implements, 허용 링크)다.
스키마와 인스턴스가 같은 폴더에 산다.

이렇게 두는 이유: 에이전트가 `objects/가설/` 를 읽으면 타입 정의와 실제 가설들이
같은 컨텍스트에 들어온다. 정의를 확인하러 다른 트리로 점프하지 않는다.

정의 본문의 표준 형태는 [[startup-object-types]] 에 타입별로 다 적혀 있다. 적용 시
그 내용을 각 개념 노트 본문으로 옮긴다.

## objects/ 를 남긴 이유

`사업체/` 를 WS 루트에 바로 두지 않고 `objects/` 아래 둔다. 그러면 `objects/` 폴더가
개념 venture-knowledge 를 담당해서 8개 타입의 broader 가 한 노드로 모인다. 루트에
흩으면 타입 8개가 각각 WS top concept 에 직결돼 그래프가 평평해지고, 프리셋을 적용한
부분과 워크스페이스 고유 개념이 구분되지 않는다.

top 개념 이름이 `startup-knowledge` 가 아니라 `venture-knowledge` 인 것은 이 구조가
창업이라는 시기가 아니라 사업체 하나를 담기 때문이다. 시기 이름을 top 에 두면 사업이
자리를 잡는 순간 top 개념이 거짓이 된다.

## 원본 자료를 어디에 두는가

창업 워크스페이스는 다른 두 프리셋보다 원본 파일이 훨씬 많다. 사업계획서 hwp, 심사
결과 pdf, 인터뷰 녹취 m4a, 로고 ai 파일이 폴더의 대부분을 차지한다. 이 파일들을 객체
그래프와 어떻게 동거시키느냐가 이 레이아웃의 실무적 관건이다.

**원본은 그것을 대표하는 객체 옆에 둔다.** 별도의 `첨부/` 나 `원본/` 폴더를 만들지
않는다. 위치가 곧 분류인 구조에서 `첨부/` 는 아무 분류도 주장하지 않는 폴더이고, 한 번
만들면 분류되지 않은 파일이 거기 영구히 쌓인다.

```
objects/제출문서/사업계획서/
  사업계획서.md                     인덱스(PK). 판본 대조표와 claims
  사업계획서_v3_예비창업패키지.hwp   제출 원본. 위치로 분류
  사업계획서_v3_예비창업패키지.hwp.md         변환본(글자). 가이드 §4.10 변환기가 만든다
  사업계획서_v3_예비창업패키지.hwp.pages.pdf  변환본(쪽 그림)
  사업계획서_v4_초기창업패키지.hwp
objects/근거/2026-08-안경원-인터뷰/
  2026-08-안경원-인터뷰.md          인덱스(PK). 대상, 규모, 들은 것
  녹취-01.m4a
```

정리 기준은 하나다. **그 파일을 다시 꺼낼 때 어느 객체를 먼저 떠올리는가.** 사업계획서
원본은 제출문서 를 떠올리고, 녹취는 그 인터뷰를 떠올린다. 떠오르는 객체가 없는 파일은
아직 객체가 없다는 뜻이므로 파일을 옮기기 전에 객체를 만든다.

## 자료를 이미 폴더로 정리해 둔 사람에게

창업자 대부분이 `사업계획서/`, `지원사업/`, `고객/`, `재무/` 같은 폴더를 이미 갖고 있다.
그 구조를 통째로 버리고 `objects/` 로 옮기는 것이 정답처럼 보이는데, 그렇게 하면 적용
직후 본인이 자기 자료를 못 찾는다.

**원본 폴더를 남기고 그 위에 객체 층을 얹는다.** 원본은 `자료/` 아래에 원래 모양대로
두고, `objects/` 에는 그 자료가 무엇을 주장하고 무엇을 근거로 삼는지만 올린다. 객체
노트에서 원본을 위키링크나 상대경로로 가리킨다.

옮길지 남길지는 [[startup-apply]] 의 이관 절차에서 파일 단위로 판정하고, 이동은 승인을
받는다. 생성은 파괴적이지 않지만 이동은 상대링크를 깨뜨린다.

## 1인이 쓴다는 조건이 레이아웃에 주는 영향

[[team-ops]] 는 갱신 충돌을 전제해 노트를 잘게 쪼갰다. 이 프리셋은 그 전제를 쓰지
않는다. 대신 다른 압력이 있다.

**1. 노트 만들기의 비용이 부담이다.** 혼자 쓰는 사람에게 파일 여덟 개를 만드는 일은
그냥 안 하게 된다. 그래서 필수 프로퍼티를 최소로 잡고, 근거 는 네 줄로도 성립하게
설계했다. 완성도가 아니라 존재를 먼저 받는다.

**2. 그래도 가설 와 근거 는 쪼갠다.** 여기서 합치면 프리셋의 논지가 사라진다.
가설 노트 안에 근거를 문장으로 적으면 `sampleSize` 와 `collectedAt` 이 사라지고,
사라지는 순간 그 근거는 사업계획서의 문장과 같은 것이 된다.

**3. 서브폴더는 부속물이 쌓인 뒤에 만든다.** team-ops 는 여러 사람이 붙을 것이
예상되면 미리 만들었다. 여기서는 미리 만들지 않는다. 혼자 쓰는 폴더에 빈 서브폴더가
늘면 자료가 어디 있는지 본인이 헷갈린다.

## 부속물이 쌓이는 객체의 서브폴더 규칙

기본은 `objects/<type>/<PK>.md` 단일 파일이다. 부속 자료가 여러 개 쌓이면 **같은 이름의
서브폴더**를 만들고 인덱스 노트(PK)를 그 안에 **같은 파일명으로** 둔다. 위키링크는
파일명으로 해석되니 기존 링크는 안 깨진다.

```
objects/자금/2026-예비창업패키지/
  2026-예비창업패키지.md          인덱스(PK), 이 지원사업의 정본
  제출-증빙-목록.md               부속 노트. frontmatter subject: 로 소속 명시
  공고문.pdf                      비-md 첨부. 위치로 분류
```

주의: 이 서브폴더는 개념 폴더가 아니다. 개념 노트를 두지 않으며, 안의 파일은 상위 타입
폴더가 아니라 **이 서브폴더 위치**로 분류된다. lint 가 고아로 잡지 않게 하려면 부속
md 에 `subject: ["[[<type>]]"]` 를 적는다. 인덱스 노트는 파일명이 곧 PK 이므로 예외
없이 `subject` 를 적는다.

상위 인덱스 노트를 가리킬 때 `자금:` 처럼 타입명을 딴 임의 키를 만들지 않는다.
술어 표에 없는 키는 규칙 10 위반이다. 다용도 연결로 등재된 `relatedObjects` 를 쓰거나
본문 위키링크로 가리킨다. 상세는 [[startup-lint]].

## 프리셋이 건드리지 않는 것

`CONTEXT.md` 의 프로토콜 항목, 포털(`AGENTS.md`, `CLAUDE.md`), `CONTEXT_GUIDE.md`, `memory/`, action-log 의 시간축 규칙은 전부 프로토콜
소관이다. 프리셋은 `objects/`, `object-sets/`, `object-views/`, `datasources/` 를
추가하고, `_project.md` 의 suitability 와 `_schema/` 에 확장을 병합하고, action-log 에
액션 어휘를 얹는 것까지만 한다.
