# 인테이크: 프리셋을 질문으로 채운다

프리셋을 얹으면 폴더와 개념 노트는 생기지만 객체는 [[compliance-apply]] Step 5 에서
세운 사슬 한 갈래뿐이다. 이 문서는 그 빈 그래프를 사용자와의 문답으로 채우는 절차다.

트리거: "컴플라이언스 프리셋 세팅해줘", "규정 체계 초기 세팅", "프리셋 채워줘",
또는 [[compliance-apply]] Step 5 를 마친 직후 자동 제안.

위치: 프리셋 호출 계약 4단계 중 3단계 끝자락이다. 프리셋 얹기(3)가 끝나고 기존 파일
정리(4)로 넘어가기 전에 돈다. 빈 워크스페이스면 4단계가 없으므로 인테이크가 마지막이다.

## 전제: 이 문답을 받는 사람

**컴플라이언스·법무·보안 실무자다. 비개발자 일반이 아니다.**

[[personal-rag-intake]] 와 대상이 다르고, 그 차이가 이 문서의 규칙 절반을 바꾼다.
그쪽 전제는 "이 사람은 자기 도메인 용어조차 없다"였다. 여기는 반대다. 이 사람은
자기 도메인에서 우리보다 낫다.

이 사람이 이미 아는 것: 법령과 시행령의 관계, 사내 규정 체계, 이행 의무, 내부통제,
이행 증거, 감사와 지적사항, 시정 기한. 이 단어들을 풀어 설명하면 오히려 불신을 산다.
"규정이란 조직이 스스로 만든 규범인데요" 를 듣는 순간 이 에이전트는 초심자로 분류된다.

이 사람이 모르거나 관심이 없는 것: 폴더와 파일 구조, frontmatter, 위키링크, 온톨로지,
술어, 인스턴스, 인터페이스, PK, lint. 프로토콜 파일 묶음을 받았지만 읽지 않았다.

여기서 따라 나오는 것들.

1. **경로를 화면에 띄우지 않는다.** `objects/obligations/분기-접근권한-검토.md` 는
   사용자 관심사가 아니다. 파일이 어디 저장됐는지는 전부 끝난 뒤 완료 보고에서 한 번만
   말한다.
2. **YAML, frontmatter, 코드 블록을 보여주지 않는다.** 사용자가 볼 화면에는 사람 문장만
   나간다.
3. **왜 이렇게 저장하는지 설명하지 않는다.** 물으면 답하되 먼저 꺼내지 않는다.
4. **기술적 결정을 승인받지 않는다.** 타입을 새로 만들지, 파일명을 뭘로 할지, 링크를
   어느 쪽에 걸지는 전부 에이전트가 정한다. 사용자에게 물어야 할 것은 사실뿐이다.
5. **도메인 판단은 반대로 반드시 사용자에게 받는다.** 이것이 personal-rag 와 가장 크게
   갈리는 지점이다. 어떤 조문이 우리에게 적용되는지, 어떤 의무가 우리 것인지, 어떤
   미비가 지적사항인지는 **법적 판단**이고 에이전트가 대신하면 안 된다. 기술 결정은
   묻지 말고, 도메인 결정은 지어내지 말라는 것이 한 쌍이다.
6. **라운드 번호나 내부 용어로 진행을 알리지 않는다.** R0~R8 은 이 문서 안에서만 쓰는
   이름이다.
7. **사용자가 모르겠다고 하면 그 라운드를 접는다.** 이 도메인에서 "모르겠다" 는 대개
   "그 부분은 다른 팀 소관" 이라는 뜻이다. 그것 자체가 정보이므로 그대로 기록한다.
8. **한 문항에 한 가지만 묻는다.**

## 왜 질문지가 필요한가

이 프리셋의 실패 모드는 "규정 목록은 있는데 사슬이 없음"이다. 축적은 대화가 일어나야
작동하는데, 워크스페이스를 막 받은 조직은 아직 이 에이전트와 대화한 이력이 없다.

질문지는 그 부트스트랩 구간만 메운다. 전수 조사가 아니다. **규정 전체를 이 문답으로
등록하려 들지 않는다.** 목표는 "사슬이 두세 갈래 끝까지 서 있고, 조직 단위가 채워져
있고, 열린 지적사항이 다 들어와 있는 상태"이고, 그 뒤는 축적에 맡긴다.

## 도구 제약과 그로부터 나오는 규칙

AskUserQuestion 은 한 콜에 최대 4문항, 문항당 2~4개 선택지 + 자동 제공되는
Other(자유입력)다. 이 모양이 인테이크 설계를 강제한다.

1. **선택지로 받을 것과 값으로 받을 것을 가른다.** 분기, 범위, 깊이, 갈래는 선택지가
   낫다. 규정명, 조문 번호, 날짜, 부서명 같은 값은 선택지로 못 만든다. 값형은 폼으로
   받는다.
2. **한 콜 4문항을 넘기지 않는다.** 라운드를 쪼갠다. 라운드 사이마다 파일을 쓴다.
3. **모든 문항에 탈출구를 둔다.** "건너뛰기", "나중에", "다른 팀 소관" 중 하나가 항상
   선택지에 있어야 한다. 없으면 사용자가 없는 사실을 만들어낸다. 이 도메인에서 지어낸
   사실은 다른 도메인보다 훨씬 비싸다. 근거 없는 `met` 하나가 감사에서 통째로
   무너진다.
4. **라운드가 끝날 때마다 즉시 파일로 쓴다.** 다 모아서 마지막에 쓰지 않는다.
   인테이크는 중간에 끊기는 것이 정상이라고 전제한다. 실무자는 회의에 불려 간다.

## 질문 문구 규약 (어휘 분리)

**사용자에게 스키마 어휘를 노출하지 않는다. 도메인 어휘는 감추지 않는다.**

이 구분이 이 프리셋 인테이크의 핵심이다. personal-rag 는 Person 과 Event 를 감췄지만
그것은 스키마 용어인 동시에 사용자에게 낯선 말이었기 때문이다. 여기서는 "의무" 와
"증거" 가 스키마 타입명이면서 동시에 **사용자가 매일 쓰는 업무 용어**다. 그것을 감추면
질문이 더 어려워진다. "그 일을 꼭 해야 하는 이유가 되는 것들" 은 "이행 의무" 보다
불친절하다.

감출 것은 구조 어휘다. 도메인 어휘는 그대로 쓴다.

| 쓰지 않는 말 | 대신 |
|---|---|
| 객체, 인스턴스, 노트, 타입 | (생략하거나) 항목 |
| 프로퍼티, 필드, frontmatter | (생략하고 그냥 그 값을 묻는다) |
| 술어, 링크, 위키링크, 정본 방향 | (사용자에게 말하지 않는다) |
| PK, slug | (에이전트가 정한다. 묻지 않는다) |
| Unit / Statute / Control 같은 영문 타입명 | 조직 단위나 부서 / 법령 / 통제 |
| Cadence, ComplianceStatus, Recurring | 주기 / 이행 상태 |
| Finding 으로 승격할까 | 이건 지적사항으로 걸린 건가요 |
| notApplicable 로 둘까요 | 우리한테는 해당 안 되나요 |
| 사슬, 그래프, 마디 | (설명이 필요하면 "법령에서 증거까지 이어지는 흐름") |
| 타입이 없으면 새로 만든다 | (사용자에게 말하지 않는다. 에이전트가 알아서 한다) |

그대로 쓰는 말: 법령, 시행령, 고시, 규정, 지침, 절차서, 의무, 통제, 증거, 감사, 점검,
지적사항, 시정, 소관 부서, 기한, 주기, 미이행. 풀어 쓰지 않는다.

**한 가지 예외.** "통제" 는 실무에서 두 뜻으로 쓰인다. 내부통제 일반과 개별 통제 활동
이다. 첫 질문에서 개별 활동을 뜻한다는 것을 한 번만 예시로 알린다. "예: 분기 첫 주에
IAM 리포트를 뽑아 팀장이 승인" 처럼 실제 활동 하나를 보여주면 그 뒤로는 어긋나지
않는다.

문항 자체도 사용자의 목적어로 쓴다. "Obligation 인스턴스를 생성할 항목을 고르세요"가
아니라 "이 규정에서 우리가 해야 하는 일이 뭐뭐인가요"다.

### 사용자가 아는 단위로만 묻고 나머지는 파생한다

실무자라도 아는 단위와 모르는 단위는 갈린다. **소관과 무관한 것은 묻지 않는다.**

보안팀 담당자에게 법령 조문 번호를 요구하면 막힌다. 법무팀에게 IAM 리포트 생성 주기를
물어도 막힌다. 둘 다 이 워크스페이스에는 필요하지만 한 사람에게 다 받을 수는 없다.

그래서 R0 에서 **응답자의 소관**을 먼저 받고, 소관 밖 라운드는 값을 캐지 말고
"어느 팀에 물어야 하나" 만 받아 pending 으로 남긴다. 그 팀 이름이 Unit 인스턴스가
되므로 빈손이 아니다.

같은 판단을 다른 곳에도 적용한다. 조문 번호를 모르면 법령명과 대략의 주제만 받고
에이전트가 원문에서 찾는다. 규정 버전을 모르면 시행일만 받는다. 정확한 경로 대신
"어느 시스템에 있는지" 를 받는다.

### 이 도메인에서 특히 어려운 질문

두 가지가 반복해서 막힌다. 미리 대응을 정해 둔다.

**"이 의무는 지키고 있나요."** 이 질문을 그대로 던지면 대부분 "네" 라고 답한다.
사람은 자기 업무가 미비하다고 먼저 말하지 않고, 실제로 지키고 있다고 믿는 경우도 많다.
그런데 이 프리셋에서 `met` 은 믿음이 아니라 증거에서 도출되는 값이다(규칙 15).

그래서 상태를 직접 묻지 않는다. **증거를 묻는다.** "그게 돌아갔다는 걸 나중에 보여줘야
하면 뭘 꺼내시나요." 꺼낼 것이 있으면 `met` 후보이고, "그건 좀 찾아봐야 한다" 면
`partial` 이고, 없으면 `unmet` 이다. 상태는 에이전트가 답에서 도출한다.

**"이건 우리한테 해당 안 됩니다."** `notApplicable` 이 가장 남용되는 값이다(규칙 18).
반박하지 말고 **이유만 한 줄 받는다.** "매출 기준 미달이라" 나 "해당 사업을 안 해서"
같은 한마디면 충분하고, 그것이 없으면 저장하지 않는다. 이유를 못 대는 비해당은
비해당이 아니라 미검토이므로 그렇게 기록한다.

## 값형 라운드는 폼으로 받는다 (빈 폼)

값형 라운드를 평문으로 묻는 것은 차선이다. 칸이 나뉜 폼이 문장 쓰기보다 싸다. 평문으로
네 가지를 물으면 사용자는 답변을 구성해야 하고, 대개 일부만 답하거나 어느 답이 어느
질문인지 모호해진다. 폼은 그 두 문제를 동시에 없앤다.

도구는 elicitation 폼이다(`show_widget`). 한 화면에 여러 칸을 놓고 한 번에 제출받는다.
AskUserQuestion 은 선택지가 본체라 값 입력에 맞지 않는다. 분기와 범위를 물을 때만 쓴다.

### 폼은 비운 채로 준다

**에이전트가 추측한 값을 미리 채우거나 선택지로 올리지 않는다.** 업종을 넘겨짚어
"개인정보보호법, 정보통신망법, 전자금융거래법" 을 선택지로 올리면, 사용자가 받는 것은
자기 폼이 아니라 남이 쓰다 만 폼이다.

해로운 이유는 세 겹이다.

1. **앵커링.** 고치는 비용이 수락하는 비용보다 크면 사용자는 그냥 고른다. 이 도메인
   에서는 더 나쁘다. 그럴듯한 법령 목록은 전문가에게도 반박하기 번거롭고, 한 번
   수락되면 "우리에게 적용되는 법령" 으로 굳는다.
2. **출처 소실.** 수락된 추측은 진술된 사실과 파일 안에서 구분되지 않는다. 감사에서
   근거를 물으면 답할 것이 없다.
3. **신뢰 손상.** 어디까지가 확인된 것이고 어디부터가 추측인지 알 수 없다.

placeholder 는 형식 안내로만 쓴다. "예: 개인정보보호법 29조" 처럼 실제 해당할 법한
값은 placeholder 라도 쓰지 않는다. "예: 법령명 + 조문 범위" 가 맞다.

### 자료 제출 칸을 폼 맨 위에 둔다

폼의 첫 그룹은 파일 업로드와 위치 입력이다. 수기 입력 칸보다 **위에** 놓고, 자료를
주면 아래는 대부분 비워도 된다고 라벨에 적는다. 싼 경로를 위에 두는 것이 요점이다.

이 도메인은 자료가 있을 확률이 다른 도메인보다 훨씬 높다. 규정 목록 엑셀, 이행 점검
체크리스트, 지난 감사 결과보고서가 대개 이미 있다. 그것을 받으면 R2~R7 이 통째로
확인 단계로 바뀐다.

- 파일: 드롭존 + 같은 그룹 안에 붙여넣기용 textarea. 파일이 없어도 본문을 붙여넣을 수
  있어야 한다.
- 위치: 규정 정본이 있는 시스템과 경로. 여기 들어온 값은 **두 곳에 쓰인다.** 규정
  노트의 `location` 이자 `datasources/` 항목이다. 같은 입력을 두 번 묻지 않는다.

받은 자료로 값을 채운 뒤에는 반드시 확인 단계를 거친다. 각 값에 어디서 가져왔는지 한
줄로 붙인다("규정목록.xlsx 12행에서"). 출처 표시가 없으면 사용자는 그것이 자기 자료에서
온 것인지 추측인지 구분할 수 없고, 그러면 빈 폼 원칙을 지킨 의미가 사라진다.

충돌 규칙: 사용자가 폼에 직접 적은 값이 자료에서 뽑은 값을 이긴다. 자료 쪽 값은 버리지
말고 확인 단계에서 "목록에는 이렇게 되어 있는데 어느 쪽이 맞나요"로 한 번 묻는다.
이 도메인에서 그 불일치 자체가 발견 사항일 때가 있다. 대장과 실제가 다른 것은 흔한
지적사항이다.

**규정 원문을 워크스페이스에 적재하지 않는다.** 업로드받은 것은 사실 추출에만 쓰고,
원본은 있던 자리를 가리킨다([[compliance]]).

### 개수와 분량은 묻지 않는다

**"규정이 몇 개인가요" 선택지 + 자유입력 칸**의 조합은 성립하지 않는다. 선택이 뒤이은
입력을 구속하지 못하면 그 문항은 클릭만 늘린다. **적은 개수가 곧 답이다.**

정밀도 선택지도 대부분 불필요하다. 이런 문항의 진짜 기능은 제약이 아니라 **허락**이다.
"조문 번호를 모르면 법령명만 적으셔도 됩니다" 가 선택지 세 개보다 낫다.

선택지가 정당한 경우는 하나다. **그 답이 에이전트의 행동을 바꾸고, 자유입력으로는
표현되지 않을 때.** 어느 사슬 갈래부터 채울지, 법령 원문을 찾아볼지 말지가 그렇다.

완결성은 나중에 묻는다. "이게 전부인가요"는 목록을 손에 쥔 확인 단계의 질문이다.

### 그럼 초안은 언제 쓰나

**출처가 사용자이거나 법령 원문일 때만.**

- 사용자가 원자료를 준 뒤: 값을 채워 보여주고 확인받는다. 받아쓰기다. 각 값에 출처를
  한 줄로 붙인다.
- 사용자가 방금 말한 내용을 정리한 경우: "이렇게 정리했는데 맞나요"는 정당하다.
- **법령 원문을 읽은 경우: 조문 요약은 초안으로 낼 수 있다.** 이것이 personal-rag 에
  없는 예외다. 원문은 공개된 1차 자료이고 확인 가능하므로 추측이 아니다. 다만 "이
  조문이 우리 조직에 적용되는가" 는 초안으로 내지 않는다. 그것은 원문에 안 적혀 있고
  법적 판단이다.
- 아무것도 받은 것이 없는 상태: 빈 폼. 예외 없다.

확인받지 못한 값은 저장하지 않는다.

## 물어보지 않는 것

- 개인의 징계 이력, 인사 평가, 특정 임직원의 위반 사실. 이 프리셋은 사람을 객체로
  두지 않는다([[compliance]]). 지적사항은 조직 단위에 붙는다. 사용자가 자발적으로
  말해도 개인을 특정해 저장하지 않는다.
- 진행 중인 소송이나 수사의 내용. 대상 워크스페이스에 별도 규칙이 없으면 건드리지
  않는다. 필요하면 사용자가 먼저 지시한다.
- 증거 원본의 내용 자체. 접근 로그의 행, 결재 이력의 항목을 받아 적지 않는다. 무엇이
  어디에 있는지만 받는다.
- 답을 안 한 값. 빈칸으로 둔다. 추론해서 채우지 않는다. 추론값을 넣어야 하는 상황이면
  `confidence: low` 와 `sources:` 에 "인테이크 추정"을 남긴다. 이 도메인에서 추정값을
  `met` 이나 `notApplicable` 에 넣는 것은 특히 금지다.

## 라운드 구성

각 라운드 = AskUserQuestion 1콜 또는 폼 1개. `[MC]` 는 선택지가 본체, `[폼]` 은 값을
받는 라운드다.

| # | 라운드 | 형 | 산출 |
|---|---|---|---|
| R0 | 오리엔테이션 | MC | 깊이 프로파일, 응답자 소관, `_project.md` 방향 |
| R1 | 조직 단위 | 폼 | `objects/units/*`. 자료 제출 칸이 여기 붙는다 |
| R2 | 적용 법령 | 폼 | `objects/statutes/*` |
| R3 | 사내 규정 | 폼 | `objects/regulations/*` + basedOn |
| R4 | 이행 의무 | 폼 | `objects/obligations/*` + requiredBy, ownedBy |
| R5 | 통제 | 폼 | `objects/controls/*` + implements, ownedBy |
| R6 | 증거 | MC+폼 | `objects/evidence/*` + evidenceFor, producedBy. 의무 상태 도출 |
| R7 | 점검과 지적사항 | 폼 | `objects/audits/*`, `objects/findings/*` |
| R8 | 마감 | MC | `object-sets/*`, `object-views/*`, `datasources/*`, lint, 축적 인계 |

순서가 사슬 순서와 같다. 위에서 아래로 내려가야 각 라운드가 앞 라운드의 답을 붙일
자리를 갖는다. Unit 이 맨 앞인 이유는 R3 부터 모든 라운드가 `owner` 를 요구하기
때문이다.

### 깊이 프로파일

R0 에서 사용자가 고른다. 라운드 수가 곧 소요 시간이다.

| 프로파일 | 도는 라운드 | 콜 수 | 이 상태로 답할 수 있는 것 |
|---|---|---|---|
| seed | R0, R1, R3, R4, R8 | 5콜 | 규정 대장과 의무 목록. "무엇을 지켜야 하나" |
| standard | R0~R6, R8 | 9콜 | 사슬이 증거까지 선다. "지키고 있다는 근거가 뭐냐" |
| full | R0~R8 전체, 인스턴스 많은 라운드는 2회전 | 13콜 이상 | 감사 대응 준비 상태 |

콜 수는 라운드 수와 다르다. **R6 은 라운드 하나에 콜 둘이다.** 어느 의무부터 볼지를
선택지로 받고(AskUserQuestion) 그 다음에 값을 폼으로 받는다. 그래서 standard 는
라운드 여덟 개에 콜 아홉 번이다. full 은 여기에 R2 와 R7 이 더해지고(11콜) 인스턴스가
많은 라운드를 한 번 더 도는 몫이 붙는다.

콜 수를 세는 이유는 하나다. 사용자에게 남은 시간을 말할 때 라운드가 아니라 콜을
기준으로 해야 어긋나지 않는다. 라운드 번호는 화면에 안 쓰지만 "절반쯤 왔어요" 는
콜 기준으로 판단한다.

기본값은 standard 다. **seed 는 이 프리셋에서 반쪽이다.** 증거가 없으면 이 워크스페이스가
답해야 하는 질문에 답하지 못한다. seed 를 고른 사용자에게는 나중에 "증거까지 마저
채울까요"를 제안할 수 있게 진행 상태를 남긴다(아래 재개 규약).

**감사가 코앞이면 순서를 뒤집는다.** R0 에서 "곧 감사가 있다"가 나오면 R7 을 먼저 돌아
열린 지적사항부터 받는다. 기한이 지난 지적이 있으면 그것이 지금 가장 급한 사실이고,
사슬을 다 세운 뒤에 발견할 것이 아니다.

## 라운드별 질문 대본

아래는 무엇을 물을지만 적었다. 실제 문구는 위 "질문 문구 규약"에
맞춰 다시 쓴다. 지킬 것은 무엇을 묻는가와 탈출구 유무 둘뿐이다. 아래 표기에 남아 있는
Unit, Statute 같은 영문 타입명은 전부 에이전트용이며 화면에 그대로 나가면 안 된다.

### R0 오리엔테이션 [MC]

1. 이걸로 주로 뭘 하려는지 (multiSelect)
   - 규정 체계 정리 / 이행 증거 상태 점검 / 감사 대응 준비 / 법령 개정 영향 추적
   - "감사 대응 준비" 가 선택되면 R7 을 앞으로 당긴다.
2. 어느 정도까지 채울지
   - 규정과 의무까지 / 증거까지 (권장) / 점검 이력까지 전부
   - 깊이 프로파일 seed / standard / full 에 대응한다. 프로파일 이름은 화면에 안 쓴다.
3. 답하시는 분 소관이 어디까지인지 (multiSelect)
   - 법령·규정 / 이행과 증거 / 감사와 시정 / 조직 전반
   - 이 답으로 소관 밖 라운드를 가른다. 소관 밖에서는 값을 캐지 않고 "어느 팀에
     물어야 하나" 만 받는다.
4. (비워 둠) 원래 "이미 정리해둔 자료가 있는지"를 물었으나 R1 폼의 자료 제출 칸으로
   옮겼다. 묻고 나서 낼 자리를 다음 턴에 만들면 한 턴이 낭비된다. 자료를 냈는지 여부가
   곧 답이다. R0 는 세 문항으로 충분하다.

### R1 조직 단위 [폼]

**폼 맨 위가 자료 제출 그룹이다.** 규정 목록, 점검 체크리스트, 지난 감사 결과보고서를
받는다. 그 아래에 규정 정본이 있는 시스템과 경로 칸을 둔다.

그 아래 조직 단위 칸. 부서·팀·위원회 이름과 각 단위가 지는 책임 범위를 받는다. 현재
담당자 이름은 **선택**이고, 라벨에 "바뀌면 여기 한 줄만 고치면 됩니다" 를 적는다.
그 한 줄이 왜 사람이 아니라 조직에 책임을 거는지를 설명 없이 전달한다.

개수를 묻지 않는다. 위원회를 넣을지 말지도 묻지 않는다. 적으면 만들고 안 적으면 없다.

경계: **이름만 있는 Unit 을 대량 생성하지 않는다.** 조직도를 통째로 받아 넣으면 대부분
아무 링크도 안 붙은 채 남는다. 사슬에 실제로 걸릴 단위만 만든다. 조직도가 필요하면
나중에 `partOf` 로 채운다.

### R2 적용 법령 [폼]

법령명과 적용 조문, 소관 기관을 받는다. 조문 번호를 모르면 법령명과 주제만 받는다.
라벨에 "조문 번호를 모르면 법령명만 적으셔도 됩니다" 를 넣는다.

**한 인스턴스 = 조직에 적용되는 조문 묶음**이다([[compliance-object-types]]). 사용자가
법령명만 적어도 에이전트가 통째로 한 노트에 넣지 않는다. 어느 조문이 걸리는지 모르면
그 상태로 남기고 `articles` 를 비운다.

원문 확인: 사용자가 허락하면 법령 원문을 찾아 `summary` 초안을 낸다. 찾은 원문은
`datasources/` 에 등록한다. **적용 여부 판단은 초안으로 내지 않는다.**

seed 프로파일에서는 이 라운드를 건너뛴다. 규정에서 위로 역추적하는 것은 시간이 걸리고
법무 확인이 필요하다. `basedOn` 이 빈 Regulation 은 위반이 아니다.

### R3 사내 규정 [폼]

규정명, 종류, 판 번호, 시행일, 소관 부서, 정본 위치를 받는다.

**`location` 을 비운 채로 넘어가지 않는다.** 이 타입에서 가장 자주 빠지고 가장 아픈
값이다. 정확한 경로를 모르면 시스템 이름만이라도 받는다. R1 에서 받은 시스템 경로가
있으면 그것으로 채우고 확인받는다.

R2 를 돌았으면 각 규정의 근거 법령을 잇는다. 사용자가 모르면 비워 두고 pending 으로
남긴다.

폐지된 규정도 받는다. 라벨에 "지금은 안 쓰는 규정도 적어주세요" 를 넣는다. 과거 기간의
증거가 근거를 가지려면 그 시점에 유효했던 판이 있어야 한다. 사용자는 대개 현행만
떠올리므로 이 한 줄이 필요하다.

### R4 이행 의무 [폼]

규정별로 "이 규정에서 우리가 해야 하는 일" 을 받는다. 항목마다 주기, 기한 규칙, 소관
부서. 미이행 시 제재가 있으면 그것도.

**의무와 통제를 섞어 적는 것이 이 라운드의 기본 오류다.** 사용자가 "분기 첫 주에 IAM
리포트를 뽑아 팀장이 승인" 이라고 적으면 그것은 의무가 아니라 통제다. 되묻지 말고
에이전트가 가른다. 판별은 [[compliance]] 의 "없어져도 되는 쪽이 Control 이다".
갈라 놓고 확인 단계에서 "이렇게 나눴는데 맞나요" 로 한 번 보여준다.

`requiredBy` 없이 만들지 않는다(규칙 14). 근거를 못 대는 항목은 의무가 아니라 관행일
수 있고, 그 구분 자체가 사용자에게 유용한 발견이다.

`status` 를 이 라운드에서 묻지 않는다. R6 에서 증거로부터 도출한다.

### R5 통제 [폼]

의무별로 "그걸 실제로 어떻게 하고 있는지" 를 받는다. 절차, 쓰는 시스템, 실행 주기,
수동인지 자동인지, 운영 부서.

수동·자동 구분은 선택지로 받아도 된다. 세 갈래로 닫히고 자유입력으로는 표현되지 않는다.

의무는 있는데 통제가 없다고 답하면 **그대로 기록한다.** 빈칸이 아니라 공백이다. R8 에서
그 목록이 나온다. 여기서 "그럼 뭐라도 하고 계시겠죠" 로 유도하지 않는다.

### R6 증거 [MC+폼]

1. 어느 의무부터 볼지 (multiSelect, 앞에서 나온 의무를 선택지로) / 전부 / 지금은 안 함
2. 의무별 폼: 그게 돌아갔다는 걸 나중에 보여줘야 하면 뭘 꺼내는지, 그것이 덮는 기간,
   어디에 있는지, 누가 모으는지.

**상태를 직접 묻지 않는다.** 위 "이 도메인에서 특히 어려운 질문" 대로 증거를 묻고
상태는 답에서 도출한다. 도출 결과를 확인 단계에서 보여준다. "이건 증거가 지난 분기
것까지만 있어서 부분 충족으로 뒀습니다" 처럼 근거를 붙여 보여주면 사용자가 반박하거나
빠진 증거를 떠올린다. 둘 다 이득이다.

`coversFrom` 과 `coversTo` 를 비운 채 저장하지 않는다. 끝이 없는 증거는 증거가 아니다.
기간을 모르면 그 항목은 증거가 아니라 "증거가 있을 것 같은 자리" 이므로 만들지 않고
pending 으로 남긴다.

원본을 워크스페이스에 들이지 않는다. 위치만 받는다.

### R7 점검과 지적사항 [폼]

1. 지난 점검: 점검명, 종류, 시기, 수행 주체, 결과.
2. 열린 지적사항: 무엇이 문제인지, 등급, 제기 시점, 시정 기한, 시정 책임 부서.

**닫힌 지적사항까지 다 받으려 하지 않는다.** 열린 것과 최근 한 회차면 충분하다. 과거
지적 전체는 축적으로 들어온다.

`dueAt` 이 이미 지난 것이 나오면 그 자리에서 알린다. 인테이크 중에 나온 발견이라도
발견이다. 조용히 저장하고 R8 에서 보고하지 않는다.

Finding 으로 만들지 로그 한 줄로 둘지의 판단 기준은 [[compliance-actions]] 의
"Finding 으로 승격하는 기준" 을 따른다. 사용자가 "그건 지적까지는 아니고" 라고 하면
그 말이 판정이다.

### R8 마감 [MC]

1. 어떤 현황표를 만들어 둘까 (multiSelect): 이행 현황 / 증거 없는 의무 / 열린 지적사항 /
   기한 임박 목록 / 만들지 않음
   - object-sets 와 object-views 는 결과를 박지 않고 **필터 명세**로 적는다. 그래야
     스테일해지지 않는다([[compliance-lint]]).
2. 앞으로 새 사실이 나오면: 물어보지 말고 바로 기록 (권장) / 매번 확인받기
   - 답을 `memory/` 에 사용자 선호로 남긴다. GUIDE §12 능동적 축적의 강도 설정이다.

마감에서 에이전트가 하는 일: object-sets/object-views 생성, `datasources/` 등록,
[[compliance-lint]] 실행, `_project.md` 와 `memory/MEMORY.md` 갱신, action-log 엔트리,
그리고 **채워진 것과 빈 것의 요약**을 사용자에게 보고한다.

이 프리셋의 마감 보고는 다른 프리셋과 다르다. 빈 라운드 목록만 보고하는 것이 아니라
**실질 점검 결과를 함께 보고한다.** 증거 없는 의무 몇 건, 기한 지난 증거 몇 건, 열린
채 기한 넘긴 지적 몇 건. 이것이 사용자가 이 워크스페이스를 만든 이유이고, 인테이크
직후가 그 숫자를 처음 볼 수 있는 시점이다.

숫자를 문제로 제시하지 않는다. 인테이크 직후에 공백이 많은 것은 정상이고, 그 공백
목록이 곧 다음 할 일이다.

## 답변 -> 파일 매핑

| 라운드 | 쓰는 파일 | 쓰는 방식 |
|---|---|---|
| R0 | `memory/compliance-intake.md`, `_project.md` | 프로파일과 응답자 소관을 상태로 기록 |
| R1 | `objects/units/<이름>.md` n개, `datasources/*` | 신규 |
| R2 | `objects/statutes/<slug>.md` n개, `datasources/<이름>.md` | 신규. 찾아본 법령 원문을 출처로 등록 |
| R3 | `objects/regulations/<slug>.md` n개 | 신규. `basedOn`, `ownedBy` |
| R4 | `objects/obligations/<slug>.md` n개 | 신규. `requiredBy`, `ownedBy` |
| R5 | `objects/controls/<slug>.md` n개 | 신규. `implements`, `ownedBy` |
| R6 | `objects/evidence/<slug>.md` n개 + 의무 `status` 갱신 | 신규 + 기존 갱신 |
| R7 | `objects/audits/<slug>.md`, `objects/findings/<slug>.md` n개 | 신규. `raisedBy`, `affects` |
| R8 | `object-sets/*`, `object-views/*`, `memory/MEMORY.md`, `action-log/<YYYY-MM-DD>.md` | 신규 + 인덱스 갱신 |

쓰기는 전부 GUIDE §6 쓰기 프로토콜을 탄다. 템플릿은 `templates/<타입>.md.tpl` 를 쓰고
빈 필드는 지우지 말고 빈 채로 남긴다. 나중에 무엇이 비었는지가 다음 질문거리다.

액션 로그는 라운드마다 남긴다. R6 은 `recordEvidence`, R7 은 `raiseFinding` 이다
([[compliance-actions]]).

## 중단과 재개

인테이크는 중간에 끊기는 것이 정상이다. 진행 상태는 memory-layer 사실(in-flight
status)이므로 `memory/compliance-intake.md` 에 둔다. 개념 폴더에 두지 않는다.

```yaml
---
type: document
title: compliance 인테이크 진행 상태
profile: standard
respondentScope: [법령규정, 감사시정]
updated: 2026-09-10
---

| 라운드 | 상태 | 비고 |
|---|---|---|
| R0 | done | standard, 법무 소관 |
| R1 | done | |
| R2 | partial | 조문 번호 미확인 3건 |
| R3 | done | |
| R4 | done | |
| R5 | outOfScope | 보안팀 소관. 담당 Unit 등록됨 |
| R6 | pending | R5 선행 필요 |
| R7 | done | 열린 지적 4건 |
| R8 | pending | |
```

`outOfScope` 는 이 프리셋에서만 쓰는 상태다. skipped 와 다르다. skipped 는 사용자가
안 하기로 한 것이고 outOfScope 는 **다른 사람에게 물어야 하는 것**이다. 비고에 어느
Unit 소관인지 적어 두면 다음 세션이 누구에게 물을지 안다.

`memory/MEMORY.md` 에 인덱스 한 줄을 넣는다. 전 라운드가 done 이면 이 파일을 지우지
말고 `completed` 로 상태만 바꾼다. 언제 무엇을 물었는지가 나중에 "왜 이 필드가
비었나"의 답이 된다.

## 안티패턴

| 하면 안 되는 것 | 왜 |
|---|---|
| 도메인 용어를 풀어 설명하기 | 상대는 전문가다. 초심자 취급이 불신을 산다 |
| 반대로 스키마 용어를 그대로 노출하기 | 술어와 PK 는 사용자 관심사가 아니다 |
| 적용 법령을 추측해 선택지로 올리기 | 그럴듯한 목록은 반박이 번거로워 그대로 굳는다 |
| "이 의무 지키고 계신가요" 를 그대로 묻기 | 대부분 "네" 라고 답한다. 증거를 물어야 한다 |
| 이유 없는 notApplicable 을 저장하기 | 비해당이 아니라 미검토다. 규칙 18 |
| 의무와 통제를 사용자에게 갈라 달라고 하기 | 에이전트가 가르고 확인만 받는다 |
| 기간 없는 증거를 저장하기 | 끝이 없는 증거는 증거가 아니다 |
| 규정 원문이나 증거 원본을 적재하기 | 정본이 둘이 된다. 프리셋의 "부적합" 항목 |
| 조직도를 통째로 Unit 으로 만들기 | 링크 없는 노드는 조회에 안 잡히고 lint 만 시끄럽다 |
| 개수·분량 선택지 + 자유입력 칸 조합 | 선택이 입력을 구속하지 못한다 |
| 탈출구 없는 강제 선택 | 없는 사실이 만들어진다. 이 도메인에서 특히 비싸다 |
| 답을 다 모은 뒤 한 번에 쓰기 | 중단되면 전부 날아간다. 실무자는 회의에 불려 간다 |
| 빈 상태를 추론으로 채우기 | 근거 없는 met 하나가 감사에서 통째로 무너진다 |
| 8종에 억지로 끼워맞추기 | 새 타입을 만든다([[compliance-object-types]]) |

## 완료 판정

인테이크가 끝났다고 말할 수 있는 조건. 라운드를 다 돈 것과 다르다.

1. **사슬이 두 갈래 이상 Statute 또는 Regulation 부터 Evidence 까지 끊김 없이 이어진다.**
   한 갈래는 [[compliance-apply]] Step 5 에서 이미 섰으므로 인테이크가 최소 한 갈래를
   더 세운 것이다.
2. 모든 Obligation 이 `requiredBy` 를 갖는다(규칙 14).
3. 모든 책임 술어가 Unit 을 가리키고 사람 이름 문자열이 아니다(규칙 13).
4. `status: met` 인 의무가 전부 유효한 Evidence 를 갖는다(규칙 15).
5. `notApplicable` 인 의무가 전부 이유를 갖는다(규칙 18).
6. 열린 Finding 이 전부 `owner` 와 `dueAt` 을 갖는다.
7. 모든 위키링크가 실재 노트를 가리킨다(규칙 9).
8. `memory/compliance-intake.md` 의 모든 라운드가 done / skipped / outOfScope 로
   판정돼 있다. pending 이 남아 있으면 완료가 아니라 중단이다.

1번이 안 되면 객체는 있는데 사슬이 아니다. 그 상태에서 "이 의무를 지키고 있다는 근거가
뭐냐" 를 물으면 개별 파일 grep 과 다를 바 없어진다. 이 프리셋의 존재 이유가 사슬이므로
1번을 통과 못 하면 R4~R6 을 더 돈다.

**공백은 실패가 아니다.** 증거 없는 의무가 많이 남는 것은 정상이고 그것이 이 조직의
현재 상태다. 완료 판정이 요구하는 것은 공백이 없는 것이 아니라 **공백이 공백으로
기록돼 있는 것**이다. 빈칸과 확인된 부재는 다르다.
