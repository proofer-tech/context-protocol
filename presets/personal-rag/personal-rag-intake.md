# 인테이크: 프리셋을 질문으로 채운다

프리셋을 얹으면 폴더와 개념 노트는 생기지만 객체는 루트 Person 하나뿐이다. 이 문서는
그 빈 그래프를 사용자와의 문답으로 채우는 절차다. 대상은 **context-protocol
파일만 받았고 이 구조를 처음 보는 사람**이다. 그 사람은 무엇을 적어야 하는지 모르므로
에이전트가 물어야 한다.

트리거: "personal rag 프리셋 세팅해줘", "퍼스널 RAG 초기 세팅", "프리셋 채워줘",
또는 [[personal-rag-apply]] Step 5 를 마친 직후 자동 제안.

위치: 프리셋 호출 계약 4단계 중 3단계 끝자락이다. 프리셋 얹기(3)가 끝나고 기존 파일
정리(4)로 넘어가기 전에 돈다. 빈 워크스페이스면 4단계가 없으므로 인테이크가 마지막이다.

## 전제: 이 문답을 받는 사람

**비개발자다. 그리고 Claude 를 지금까지 질문하고 답을 받는 용도로만 써 봤다.**

이 전제가 인테이크 설계의 출발점이고, 아래 규칙 대부분이 여기서 나온다. 구체적으로
이 사람은 다음을 모르거나 관심이 없다. 폴더와 파일 구조, 마크다운, frontmatter,
위키링크, 온톨로지, 스키마, 에이전트가 도구를 쓰는 방식. 프로토콜 파일 묶음을 받았지만
읽지 않았고 앞으로도 읽지 않을 가능성이 높다. Drive 폴더를 직접 열어볼 생각도 없다.

여기서 따라 나오는 것들.

1. **경로를 화면에 띄우지 않는다.** `objects/people/홍길동.md` 는 사용자 관심사가
   아니다. 파일이 어디 저장됐는지는 전부 끝난 뒤 완료 보고에서 한 번만 말한다.
2. **YAML, frontmatter, 코드 블록을 보여주지 않는다.** 사용자가 볼 화면에는 사람 문장만
   나간다.
3. **왜 이렇게 저장하는지 설명하지 않는다.** 물으면 답하되 먼저 꺼내지 않는다. 설명은
   대개 사용자가 요청한 적 없는 학습 부담이다.
4. **기술적 결정을 승인받지 않는다.** 타입을 새로 만들지, 파일명을 뭘로 할지, 링크를
   어느 쪽에 걸지는 전부 에이전트가 정한다. 사용자에게 물어야 할 것은 사실뿐이다.
   판단을 떠넘기면 사용자는 답할 근거가 없어서 아무거나 고르고, 그 아무거나가 영구히
   남는다.
5. **라운드 번호나 내부 용어로 진행을 알리지 않는다.** "R4/9 진행 중"이 아니라 "절반쯤
   왔어요". R0~R10 은 이 문서 안에서만 쓰는 이름이다.
6. **사용자가 모르겠다고 하면 그 라운드를 접는다.** 다시 설명해서 끌고 가지 않는다.
   모른다는 답은 정보이고, 그 항목이 이 사람에게 중요하지 않다는 뜻일 때가 많다.
7. **한 문항에 한 가지만 묻는다.** 두 개념을 한 문장에 넣으면 무엇에 답하는지 흐려진다.

반대 신호도 적어 둔다. 사용자가 먼저 파일 구조나 스키마를 물으면 그때는 설명해도 된다.
전제는 기본값이지 사용자를 낮춰 보는 근거가 아니다.

## 왜 질문지가 필요한가

이 프리셋의 실패 모드는 "구조는 완벽한데 비어 있음"이다. 원래 설계는 루트 하나만 만들고
GUIDE §12 능동적 축적에 맡기는 것이었는데, 축적은 **대화가 일어나야** 작동한다. 워크스페이스를
막 받은 사람은 아직 이 에이전트와 대화한 이력이 없다. 부트스트랩 구간이 비어 있는 것이다.

질문지는 그 구간만 메운다. 전수 조사가 아니다. 목표는 "루트에서 2홉으로 닿는 객체가
열 개쯤 있는 상태"이고, 그 뒤는 원래대로 축적에 맡긴다.

## 도구 제약과 그로부터 나오는 규칙

AskUserQuestion 은 한 콜에 최대 4문항, 문항당 2~4개 선택지 + 자동 제공되는 Other(자유입력)다.
이 모양이 인테이크 설계를 강제한다.

1. **선택지로 받을 것과 값으로 받을 것을 가른다.** 분기, 범위, 깊이, 갈래는 선택지가 낫다
   (사용자가 무엇을 답해야 하는지 몰라도 됨). 이름, 날짜, 조직명 같은 값은 선택지로 못 만든다.
   값형은 Other 자유입력에 태우거나, 3개 이상 나열이 필요하면 그 라운드만 평문 턴으로 내린다.
2. **한 콜 4문항을 넘기지 않는다.** 라운드를 쪼갠다. 라운드 사이마다 파일을 쓴다.
3. **모든 문항에 탈출구를 둔다.** "건너뛰기", "나중에", "잘 모르겠음" 중 하나가 항상 선택지에
   있어야 한다. 없으면 사용자가 없는 사실을 만들어낸다. 그게 이 프리셋에 가장 해로운 오염이다.
4. **라운드가 끝날 때마다 즉시 파일로 쓴다.** 다 모아서 마지막에 쓰지 않는다. 사용자가 3라운드에서
   그만둬도 2라운드까지는 남아야 한다. 인테이크는 중간에 끊기는 것이 정상이라고 전제한다.

## 질문 문구 규약 (어휘 분리)

**사용자에게 스키마 어휘를 노출하지 않는다.** 이것이 인테이크에서 가장 자주 어기는
규칙이고, 어기면 첫 질문부터 막힌다. 인테이크의 대상은 이 구조를 처음 보는 사람이다.
그 사람에게 Person, Artifact, 루트, 객체, 인스턴스, 승격, 타입은 아무 의미가 없다.
사용자의 말을 스키마로 옮기는 것은 에이전트의 일이고 사용자가 알 필요가 없다.

| 쓰지 않는 말 | 대신 |
|---|---|
| 루트 Person 노트 | 본인 / 나 |
| Person / Organization / Project | 사람 / 회사·학교 / 하는 일 |
| Event / Place / Idea / Artifact | 일어난 일 / 장소 / 관심사·잘하는 것 / 만든 것 |
| 객체, 인스턴스, 노트 | (생략하거나) 항목 |
| 축, 프로퍼티, 필드 | (생략하고 그냥 그 값을 묻는다) |
| Place 로 승격할까 | 이 동네를 따로 적어둘까요 |
| kind 를 고르세요 | 이건 어느 쪽에 가깝나요 |
| 타입이 없으면 새로 만든다 | (사용자에게 말하지 않는다. 에이전트가 알아서 한다) |

"축"은 특히 피한다. 사람이 쓰지 않는 말이라 AI 가 쓴 티가 난다. 같은 이유로 "관점",
"레이어", "차원", "요소" 같은 추상 명사로 질문을 시작하지 않는다.

문항 자체도 사용자의 목적어로 쓴다. "루트 Person 에서 채울 항목을 고르세요"가 아니라
"본인에 대해 뭐부터 적을까요"다. 앞의 문장은 시스템 사정이고 뒤의 문장은 사용자 사정이다.

### 사용자가 아는 단위로만 묻고 나머지는 파생한다

식별자를 요구할 때 특히 어긴다. **그 사람이 실제로 알고 있는 형태로만 묻는다.**

이메일 주소는 누구나 안다. 반면 캘린더 주소, 계정 ID, 워크스페이스 도메인, 프로필 URL 은
비개발자 머릿속에 없는 개념이다. "캘린더 주소를 알려주세요"를 받으면 엉뚱한 것을 적거나
캘린더에 주소가 있다는 말에 당황한다. 어느 쪽이든 그 칸은 실패한다.

캘린더는 대개 메일 계정에 딸려 있으므로 메일 주소에서 파생된다. 파생할 수 있는 것은
파생하고, 파생이 틀렸을 때만 되묻는다. 되묻는 비용이 처음부터 어렵게 묻는 비용보다 싸다.
캘린더 문항은 주소를 받지 말고 **봐도 되는지만** 묻는다.

같은 판단을 다른 곳에도 적용한다. GitHub 은 "프로필 주소나 아이디" 둘 다 받는다. 아이디만
아는 사람이 더 많다. 폴더는 정확한 경로 대신 "대략 어디쯤"을 받는다.

예외는 없다. 대상 워크스페이스의 주인이 이 프리셋을 직접 설계한 사람이더라도 그 사람이
편하려고 쓰는 말과 인테이크가 쓸 말은 다르다.

## 값형 라운드는 폼으로 받는다 (빈 폼)

값형 라운드를 평문으로 묻는 것은 차선이다. 비개발자에게 **칸이 나뉜 폼이 문장 쓰기보다
싸다.** 평문으로 네 가지를 물으면 사용자는 답변을 구성해야 하고, 대개 일부만 답하거나
어느 답이 어느 질문인지 모호해진다. 폼은 그 두 문제를 동시에 없앤다.

도구는 elicitation 폼이다(`show_widget`). 한 화면에 여러 칸을 놓고 한 번에 제출받는다.
AskUserQuestion 은 선택지가 본체라 값 입력에 맞지 않는다. 분기와 범위를 물을 때만 쓴다.

### 폼은 비운 채로 준다

**에이전트가 추측한 값을 미리 채우거나 선택지로 올리지 않는다.** 사용자 이름을 넘겨짚어
선택지에 올리고 회사명이 박힌 예시를 칸에 넣으면, 사용자가 받는 것은 자기 폼이 아니라
남이 쓰다 만 폼이다. 중고로 산 책에 앞사람 낙서가 그대로 남아 있는 것과 같다.

해로운 이유는 세 겹이다.

1. **앵커링.** 고치는 비용이 수락하는 비용보다 크면 사용자는 그냥 고른다. 그렇게 들어간
   문장은 사용자의 것이 아니라 에이전트의 추측이 사용자 이름을 달고 있는 것이다.
2. **출처 소실.** 수락된 추측은 진술된 사실과 파일 안에서 구분되지 않는다. 이 프리셋의
   가치가 근거 있는 사실에 있는데 그 근거를 첫 화면에서 오염시킨다.
3. **신뢰 손상.** 사용자는 어디까지가 이미 알려진 사실이고 어디부터가 추측인지 알 수
   없다. 비개발자에게는 특히 불투명하다.

placeholder 는 형식 안내로만 쓴다. 형식조차 사용자와 무관한 일반 예시여야 한다.
"예: 팀 프루퍼 / 대표"처럼 그 사용자에게 실제로 해당할 법한 값은 placeholder 라도
쓰지 않는다. "예: 조직 이름 / 역할 / 시작 연도"가 맞다.

### 자료 제출 칸을 폼 맨 위에 둔다

폼의 첫 그룹은 파일 업로드와 링크 입력이다. 수기 입력 칸보다 **위에** 놓고, 자료를 주면
아래는 대부분 비워도 된다고 라벨에 적는다. 싼 경로를 위에 두는 것이 요점이다.

이유는 순서다. R0 에서 "이미 정리해둔 게 있나"를 물어놓고 정작 낼 자리를 다음 턴에
만들면, 있다고 답한 사용자가 한 턴을 더 쓴다. 폼 안에 두면 자료 제출과 수기 입력이 한
동작이 되고, R0 의 그 문항은 없어도 된다. 자료를 냈는지 여부가 곧 답이기 때문이다.

- 파일: `.elicit-files` 드롭존 + 같은 그룹 안에 붙여넣기용 textarea. 파일이 없어도
  본문을 붙여넣을 수 있어야 한다.
- 링크: 폼 마지막 절의 위임 그룹에서 함께 받는다. 여기 들어온 주소는 **두 곳에 쓰인다.**
  R1~R3 초안의 근거이자 R9 의 수집 대상 겸 datasource 다. 같은 입력을 두 번 묻지 않는다.

받은 자료로 값을 채운 뒤에는 반드시 확인 단계를 거친다. 각 값에 어디서 가져왔는지
한 줄로 붙인다("이력서 2쪽의 경력 항목에서"). 출처 표시가 없으면 사용자는 그것이 자기
자료에서 온 것인지 에이전트의 추측인지 구분할 수 없고, 그러면 빈 폼 원칙을 지킨 의미가
사라진다.

충돌 규칙: 사용자가 폼에 직접 적은 값이 자료에서 뽑은 값을 이긴다. 직접 적은 것이 더
최근이고 더 의도적이다. 자료 쪽 값은 버리지 말고 확인 단계에서 "이력서에는 이렇게 되어
있는데 어느 쪽이 맞나요"로 한 번 묻는다.

프라이버시: 업로드한 파일은 대화에 첨부된다. 그것을 워크스페이스에 저장할지는 별개
판단이고, R0 의 공개 범위 답과 대상 워크스페이스의 좁힘 규칙을 따른다. 이력서를 통째로
워크스페이스에 넣지 않는다. 사실만 객체로 반영하고 원본은 datasource 로 가리킨다.

### 개수와 분량은 묻지 않는다

**"몇 개 적을까요" 선택지 + 자유입력 칸**의 조합은 성립하지 않는다. 3개라고 고르고 1개를
쓰거나 1개라고 고르고 3개를 쓸 수 있고, 그때 어느 쪽이 참인지 판정할 방법이 없다. 선택지가
뒤이은 입력을 구속하지 못하면 그 문항은 클릭만 늘린다.

**적은 개수가 곧 답이다.** 세어 보면 된다.

같은 이유로 정밀도 선택지도 대부분 불필요하다. "날짜까지 / 연월까지 / 연도만"을 고르게
해도 사용자는 항목마다 아는 만큼 쓴다. 이런 문항의 진짜 기능은 제약이 아니라 **허락**이다.
"부정확해도 된다"는 신호를 주는 것인데, 그 신호는 라벨이나 placeholder 한 줄로 충분하다.
"날짜를 모르면 연도만 적으셔도 됩니다"가 선택지 세 개보다 낫다.

선택지가 정당한 경우는 하나다. **그 답이 에이전트의 행동을 바꾸고, 자유입력으로는 표현되지
않을 때.** 수집을 어디까지 거슬러 올라갈지가 그렇다. 그것은 사용자가 무엇을 적느냐와
무관하게 에이전트가 할 일을 정한다.

완결성이 필요하면 나중에 묻는다. "이게 전부인가요"는 목록을 손에 쥔 확인 단계의 질문이다.
입력 전에 물으면 사용자는 자기가 몇 개를 떠올릴지 모른 채 답해야 한다. 사후 필터링과
같은 원리다.

### 그럼 초안은 언제 쓰나

**출처가 사용자일 때만.** 이것이 유일한 기준이다.

- 사용자가 원자료를 준 뒤(R0 에서 이력서·프로필·링크가 있다고 했고 그것을 읽은 경우):
  값을 채워 보여주고 확인받는다. 이때는 낙서가 아니라 받아쓰기다. 각 값에 어디서
  가져왔는지 한 줄로 붙인다.
- 사용자가 방금 말한 내용을 정리한 경우: "이렇게 정리했는데 맞나요"는 정당하다.
  사용자가 이미 말했으므로 앵커링이 아니라 확인이다.
- 아무것도 받은 것이 없는 상태: 빈 폼. 예외 없다.

확인받지 못한 값은 저장하지 않는다. 사용자가 그 칸을 건너뛰면 빈칸으로 남긴다.

## 물어보지 않는 것

- 건강, 종교, 정치 성향, 성적 지향, 재무 상태, 주민등록번호급 식별자. 사용자가 자발적으로
  말하면 [[personal-rag-schema]] 대로 기록하지만 **인테이크가 먼저 캐묻지 않는다**.
  프로토콜의 민감정보 규칙은 "사용자가 지시하면 쓴다"이지 "에이전트가 수집한다"가
  아니다. 대상 워크스페이스에 승인 게이트나 등급 금지 같은 좁힘 규칙이 있으면 그쪽이
  이 프리셋보다 우선한다.
- 집 주소. Place 로 필요하면 도시 단위까지만 묻는다.
- 답을 안 한 프로퍼티. 빈칸으로 둔다. 추론해서 채우지 않는다. 추론값을 넣어야 하는 상황이면
  `confidence: low` 와 `sources:` 에 "인테이크 추정"을 남긴다.

## 라운드 구성

각 라운드 = AskUserQuestion 1콜. `[MC]` 는 선택지가 본체, `[값]` 은 선택지로 갈래를 정하고
값은 자유입력으로 받는 라운드다.

| # | 라운드 | 형 | 산출 |
|---|---|---|---|
| R0 | 오리엔테이션 | MC | 깊이 프로파일, `_project.md` 방향, object-sets 후보 |
| R1 | 나 (루트 Person) | 값 | `objects/people/<이름>.md` |
| R2 | 소속 | 값 | `objects/organizations/*` + 루트의 worksAt/studiedAt |
| R3 | 하는 일 | 값 | `objects/projects/*` + 루트의 participatedIn |
| R4 | 사람 | 값 | `objects/people/*` + knows/familyOf/colleagueOf |
| R5 | 시간축 | MC+값 | `objects/events/*` |
| R6 | 장소 | MC | `objects/places/*` (R1·R2·R5 에서 나온 지명 승격) |
| R7 | 관념·스킬 | MC+값 | `objects/ideas/*` + hasSkill/interestedIn/believes |
| R8 | 산출물 | 값 | `objects/artifacts/*` |
| R9 | 수집 위임 | 폼 | 위임 범위. 이어서 커넥터·Chrome 으로 훑고 `datasources/*` |
| R10 | 마감 | MC | `object-sets/*`, `object-views/*`, lint, 축적 인계 |

### 깊이 프로파일

R0 에서 사용자가 고른다. 라운드 수가 곧 소요 시간이다.

| 프로파일 | 도는 라운드 | 대략 |
|---|---|---|
| seed | R0, R1, R2, R9, R10 | 5콜. 자기소개 한 장 나올 정도 |
| standard | R0~R5, R7, R9, R10 | 9콜. 관계망 질의와 경력 타임라인이 성립 |
| full | R0~R10 전체, 인스턴스 많은 라운드는 2회전 | 13콜 이상 |

기본값은 standard 다. seed 를 고른 사용자에게 나중에 "R3~R8 을 마저 돌까요"를 제안할 수 있게
진행 상태를 남긴다(아래 재개 규약).

## 라운드별 질문 대본

아래는 무엇을 물을지를 적은 것이지 문구 자체가 아니다. 실제 문구는 위 "질문 문구 규약"에
맞춰 사용자 언어로 다시 쓴다. 지킬 것은 무엇을 묻는가와 탈출구 유무 둘뿐이다.
아래 표기에 남아 있는 Person, Place, Event 같은 말은 전부 에이전트용이며 화면에 그대로
나가면 안 된다.

### R0 오리엔테이션 [MC]

1. 이걸로 주로 뭘 하고 싶은지 (multiSelect)
   - 나를 소개하는 글 만들기 / 사람과 관계 찾아보기 / 지금까지 해온 일 정리 /
     만든 것 모아두기
2. 얼마나 자세히 채울지
   - 조금만 (5분) / 보통 (15분, 권장) / 꼼꼼히 (30분 이상)
3. 이 내용을 누가 보는지
   - 나만 / 같이 일하는 사람들도 / 밖에 내보낼 수도 있음
   - 답이 민감도 게이트가 된다. "밖에 내보낼 수도"면 R1~R8 에서 비공개성 항목을 아예
     묻지 않는다. 게이트가 걸렸다는 사실 자체는 사용자에게 말하지 않는다.
4. (비워 둠) 원래 "이미 정리해둔 게 있는지"를 물었으나 R1 폼의 자료 제출 칸으로 옮겼다.
   묻고 나서 낼 자리를 다음 턴에 만들면 한 턴이 낭비된다. 자료를 냈는지 여부가 곧 답이다.
   R0 는 세 문항으로 충분하다. 네 번째 자리에 다른 질문을 채워 넣지 않는다.

### R1 나 [값]

본인 노트는 이미 파일이 있다(apply Step 5). 여기서는 속을 채운다.

**AskUserQuestion 을 쓰지 않는다.** 빈 elicitation 폼으로 받는다. 칸은 이름, 다르게
부르는 이름, 한 줄 소개, 사는 곳, 생년월일. 전부 선택이고 빈칸을 허용한다.

드라이런에서 확인된 것 둘. (1) 선택지로 "무엇을 채울지"를 먼저 묻는 설계는 콜 하나를
통째로 쓰고도 값을 하나도 못 받는다. 게다가 사용자는 대개 전부 고른다. 안 줄 항목은
값을 안 적으면 그만이라 선택 단계 자체가 불필요하다. (2) 그 다음에 시도한 후보 제시형
폼(이름과 소속을 추측해 선택지로 올림)은 더 나빴다. 위 "폼은 비운 채로 준다" 참조.

받은 값의 배치는 에이전트가 판단하고 사용자에게 설명하지 않는다. 이름 표기 변형은
`aliases`, 핸들·이메일은 `identifiers` 표, 도시는 Place 파일로 간다. 섞지 않는다
([[personal-rag-schema]] 귀속 규칙).

### R2 소속 [값]

지금 소속과 과거 소속을 각각 자유입력 칸으로 받는다. 조직명과 역할, 기간. 개수나 범위를
선택지로 묻지 않는다(위 "개수와 분량은 묻지 않는다"). 과거 소속 칸을 비우면 남길 것이
없다는 뜻으로 읽고, 전부인지 일부인지는 확인 단계에서 목록을 놓고 묻는다.

조직마다 `objects/organizations/<이름>.md` 를 만들고 루트에 `worksAt` 또는 `studiedAt` 을 건다.
역방향 `hasMember` 는 조직 쪽에 적지 않는다(규칙 11).

### R3 하는 일 [값]

프로젝트명, 역할, 기간, 결과를 자유입력으로 받는다. 개수를 묻지 않는다. 진행 중인지
끝났는지는 사용자가 적은 기간에서 대개 드러나고, 안 드러나면 확인 단계에서 묻는다.

`slug` 가 PK 다. 한글 프로젝트명이면 slug 를 따로 정해 파일명으로 쓰고 `name` 에 한글을 둔다.

### R4 사람 [값]

이름과 관계, 알게 된 맥락을 자유입력으로 받는다. 인원수를 묻지 않는다. 관계군(가족·동료·
친구·멘토)은 선택지로 고르게 하지 말고 라벨에 예시로 넣어 무엇을 적으면 되는지만 알린다.

경계: **이름만 있는 Person 을 대량 생성하지 않는다.** 각 인스턴스는 최소한 링크 하나 또는
"어떻게 알게 되었나" 한 줄을 가져야 한다. 그게 없으면 조회 가치가 없고 lint 만 시끄러워진다.

### R5 시간축 [MC+값]

사건명, 시점, 의미를 자유입력으로 받는다. 정밀도를 선택지로 묻지 않고 라벨에 "날짜를
모르면 연도만 적으셔도 됩니다"를 넣는다. 그 한 줄이 하는 일은 제약이 아니라 허락이고,
허락은 선택지 없이도 전달된다. 이 문장이 있어야 사용자가 날짜를 지어내지 않는다.

Event 로 승격할지 action-log 한 줄로 둘지의 판단 기준은 [[personal-rag-actions]] 를 따른다.

### R6 장소 [MC]

앞 라운드에서 이미 지명이 나와 있다. 새로 묻지 말고 **따로 적어둘지만 묻는다.**

1. 앞에서 나온 동네·도시 중 따로 적어둘 곳 (앞선 답에서 수집한 지명을 선택지로):
   (동적) / 전부 / 지금은 안 함
2. 얼마나 자세히: 도시까지 / 도시와 나라 / 건물이나 가게 단위까지

`partOf` 로 상위 장소를 건다. `parentPlace` 프로퍼티는 쓰지 않는다(원본 호환용).

### R7 관념·스킬 [MC+값]

1. 어디부터 (multiSelect): 보유 스킬 / 관심 주제 / 가치관·신념 / 자주 쓰는 도구 / 건너뛰기
2. 스킬 레벨을 표기할까: 표기함(novice~expert) / 표기 안 함
3. 항목 나열(자유입력)

`kind` 는 value / belief / interest / skill / topic / tool 중 하나로 강제한다. 사용자의 말이
어느 kind 인지 애매하면 되묻는다. 임의 배정하면 나중 조회가 어긋난다.

### R8 산출물 [값]

1. 종류 (multiSelect): 글·포스트 / 코드·레포 / 발표·자료 / 디자인·작품 / 영상 / 건너뛰기
2. 실물 파일도 워크스페이스에 둘까: 파일도 넣음 / 링크만 걸음
3. 제목·URL·시점(자유입력)

파일을 넣기로 했으면 동명 서브폴더 규칙을 쓴다([[personal-rag-layout]]).

### R9 수집 위임 [폼에서 받음]

사용자가 직접 줄 수 있는 것을 다 받은 뒤에는, 사용자가 **의도적으로 아카이빙해 둔 흔적**을
에이전트가 직접 열어 훑는다. 블로그, 개인 사이트, GitHub, LinkedIn, 이메일 같은 곳이다.
문답으로는 안 나오는 것들이 여기 있다. 사람은 자기 경력을 떠올려 말하는 데 서툴지만
이미 어딘가에 적어 뒀다.

위임 범위는 **R1 폼 마지막 절에서 함께 받는다.** 별도 라운드로 빼지 않는다. 어디를 봐도
되는지는 사실이 아니라 허락이고, 허락은 사실을 주는 자리에서 같이 받는 것이 자연스럽다.

#### 주소는 출처별 칸으로 받는다

한 칸에 "한 줄에 하나씩" 몰아 받지 않는다. 그러면 어느 주소가 어느 출처인지 맞추는
일이 사용자에게 넘어간다. 그건 에이전트가 할 일이다. 블로그, GitHub, LinkedIn 각각에
라벨이 붙은 칸을 준다.

그러면 선택지 그룹이 필요 없어진다. **주소를 적는 것 자체가 선택이다.** 어디를 봐도
되는지 고르게 한 다음 주소를 또 받으면 같은 의사를 두 번 표현하게 만드는 것이고, 둘이
어긋나면(고른 곳의 주소가 없거나, 안 고른 곳의 주소가 있거나) 해석이 모호해진다.

빈칸은 "보지 말라"는 뜻으로 읽는다. 폼을 제출했는데 수집 칸이 전부 비어 있으면 그것이
명시적 거절이다. 다시 묻지 않는다. 완료 판정 5항은 이 상태도 통과로 본다.

#### 사전 범위 지정 대신 사후 필터링

**"메일에서 무엇을 찾을까요"를 묻지 않는다.** 자기 메일함에 무엇이 들어 있는지 조망할
수 있는 사람은 없다. 답할 근거가 없는 질문이고, 근거 없이 답하게 만들면 사용자는 아무거나
적는다. 이 문서의 전제 4항(판단을 떠넘기지 않는다)을 정면으로 어기는 문항이다.

**"캘린더를 봐도 될까요"도 묻지 않는다.** 계정을 적어 준 것이 이미 허락이다. 같은 의사를
두 번 표현하게 만들면 둘이 어긋났을 때 해석이 모호해진다. 주소 칸에서 이미 정한 원칙과
같다.

대신 순서를 뒤집는다.

1. **에이전트가 검색 전략을 세운다.** 근거는 R0 의 용도다. 경력 타임라인이면 소속 변화,
   발표, 프로젝트 시작과 끝을 겨냥한 질의를 만든다. 관계망이면 반복 수신자를 본다.
2. **실행 전에 무엇을 볼지 한 줄로 말한다.** "보낸 편지함에서 최근 3년 치 중 계약이나
   입사 관련한 것을 찾아보겠습니다." 사용자는 이 시점에 멈출 수 있다.
3. **결과를 후보 목록으로 보여준다.** 사용자는 목록을 보고 거른다. 조망할 수 없던 것을
   이제는 조망할 수 있으므로 이때의 판단은 근거가 있다.
4. **거른 것만 저장한다.**

이것은 로컬 폴더의 "먼저 목록만 본다"와 같은 패턴이다. **사용자가 못 보는 것에 대해
결정하게 하지 않고, 보여준 다음 결정하게 한다.** 전체 훑기 금지는 그대로다. 좁히는 근거가
사용자가 쓴 검색어에서 에이전트가 세운 전략으로 옮겨갔을 뿐이고, 투명성은 2번과 3번이
담보한다.

민감 범주는 이 흐름에서도 제외한다. 검색 전략을 세울 때부터 병원·면접·법률·가족 관련은
겨냥하지 않고, 결과에 섞여 들어오면 후보 목록에 올리기 전에 뺀다.

#### 도구는 출처별로 고른다

커넥터가 있으면 커넥터가 낫다. 브라우저로 화면을 긁는 것보다 정확하고 빠르다.

| 출처 | 도구 |
|---|---|
| 이 PC 의 폴더 | 하네스의 호스트 파일 도구(Cowork 에서는 Desktop Commander) |
| 이메일 | 공급자마다 다르다. 아래 "이메일은 공급자를 먼저 확인한다" |
| 캘린더 | 공급자마다 다르다. 아래 "캘린더" |
| 드라이브 문서 | 해당 커넥터 |
| 블로그, 개인 사이트, 포트폴리오 | Claude in Chrome |
| LinkedIn | Claude in Chrome (로그인 세션이 필요하다) |
| GitHub | 공개 프로필이면 웹 페치, 비공개까지면 Chrome |

Chrome 이 필요한 이유는 로그인 상태다. LinkedIn 프로필이나 비공개 페이지는 세션 없이
안 보인다. 확장이 연결돼 있지 않으면 그 사실을 말하고 그 출처를 건너뛴다. 우회하지 않는다.

#### 이메일은 공급자를 먼저 확인한다

**특정 공급자를 가정하고 설계하지 않는다.** Gmail 을 전제로 짜면 한국 사용자 상당수에게
그대로 실패한다. 네이버, 다음·한메일, 카카오, 네이트, 회사 자체 메일이 흔하고 이들에는
커넥터가 없다. 커넥터가 있는 쪽(Google, Microsoft)이 오히려 소수다.

**기본 가정은 "커넥터 없음"이다.** 있으면 이득으로 친다.

공급자는 메일 주소의 도메인으로 안다. 그래서 폼에서 무엇을 찾을지와 함께 주소 또는
쓰는 메일 종류를 받는다. 도메인 하나로 접근 경로가 결정되므로 질문을 늘리지 않아도 된다.

| 도메인 | 경로 |
|---|---|
| gmail.com, Google Workspace 도메인 | Google 계열 커넥터 |
| outlook.com, hotmail.com, live.com, MS365 도메인 | Microsoft 계열 커넥터 |
| naver.com, daum.net, hanmail.net, kakao.com, nate.com 등 | 커넥터 없음 |
| 회사 자체 도메인 | 겉으로는 모른다. 되묻는다 |

회사 도메인은 뒤에 무엇이 있는지 주소만 봐서는 알 수 없다. Google Workspace 일 수도
Microsoft 일 수도 자체 서버일 수도 있다. 추측해서 커넥터를 시도하지 말고 사용자에게
"이 메일을 웹에서 열면 어떤 화면인가요"처럼 확인 가능한 형태로 묻는다.

커넥터가 없는 공급자는 두 갈래다. 어느 쪽인지는 사용자가 고른다.

- **웹메일을 브라우저로 연다.** Claude in Chrome + 로그인 세션이 필요하고, 이것은 커넥터
  허락과 별개의 허락이다(위 "도구를 임의로 갈아타지 않는다").
- **건너뛴다.** 진행 상태에 pending 으로 남기고 나머지부터 한다.

공급자별 화면 구조를 이 문서에 적어 두지 않는다. UI 는 자주 바뀌고 적어 두면 곧 틀린
지시가 된다. 검색창을 찾아 사용자가 준 조건으로 검색하고 결과 목록을 읽는다는 원칙만
지키면 공급자가 무엇이든 같은 절차로 처리된다.

#### 캘린더

타임라인 용도에서 수확이 가장 좋은 출처다. 다른 곳은 사실을 문장에서 뽑아내야 하지만
캘린더는 **날짜와 참석자가 이미 구조화돼 있다.** 사람이 기억으로는 못 떠올리는 것도
남아 있다. 언제 어느 회사 사람들과 처음 만났는지, 어느 시점부터 어떤 회의에 들어갔는지.

공급자 판별은 이메일과 같다. 캘린더는 대개 메일 계정에 딸려 있으므로 폼에서 받은 메일
주소로 함께 판단한다. 다른 계정을 쓰면 사용자가 말해준다. Google 과 Microsoft 는 커넥터가
있고, 네이버 캘린더나 Apple 캘린더는 없으므로 브라우저 아니면 건너뛰기다.

##### 시끄러움을 거르는 규칙

캘린더는 밀도가 높은 만큼 잡음도 많다. 매일 있는 스탠드업과 점심 약속을 전부 Event 로
만들면 타임라인이 아니라 로그가 된다. 그래서 무엇을 승격할지 기준을 둔다.

| 캘린더에 있는 것 | 무엇으로 |
|---|---|
| 반복 일정 (주간 회의, 스탠드업) | Event 아님. 그 조직·프로젝트에 **속해 있었다는 근거**로만 쓴다. 반복 구간의 시작과 끝이 소속 기간을 말해준다 |
| 1회성이고 제목이 고유하고 참석자가 많음 | Event 후보 (발표, 워크숍, 킥오프) |
| 여행, 출장 | Event 후보. Place 도 함께 생긴다 |
| 반복 1:1 | Event 아님. 그 사람과의 관계 근거 |
| 개인 일정 (병원, 면접, 가족 행사) | **후보에서 뺀다.** 아래 참조 |

반복 일정을 소속 기간의 근거로 쓰는 것이 이 출처의 진짜 값이다. "2024년 3월부터 2025년
11월까지 그 회의에 있었다"는 이력서보다 정확하다.

##### 캘린더에서 특히 조심할 것

1. **민감 일정을 후보로 올리지 않는다.** 병원, 면접, 상담, 법률, 가족 관련은 사용자가
   명시적으로 넣으라고 하지 않는 한 목록에서 제외한다. 물어보지도 않는다. 이 프리셋의
   "물어보지 않는 것"이 캘린더에서는 자동 수집으로 우회될 수 있어서 명시해 둔다.
2. **참석자 명단이 곧 인맥이 아니다.** 한 번 같은 회의에 있었다고 Person 을 만들지
   않는다. 반복해서 나타나거나 사용자가 확인해준 사람만 만든다. 안 그러면 회사 전체
   주소록이 "아는 사람"으로 들어온다.
3. **제목만 보고 의미를 지어내지 않는다.** "김대표 미팅"이 무슨 일이었는지는 캘린더가
   말해주지 않는다. 사건이 있었다는 사실만 기록하고 의미는 사용자에게 받는다.
4. **초대받았을 뿐 안 간 일정이 섞인다.** 응답 상태를 확인할 수 있으면 거절·미응답은
   제외한다. 확인할 수 없으면 후보에 "참석 여부 불명"으로 표시해 사용자가 거른다.

#### 이 PC 의 폴더

온라인에만 흔적이 있는 것이 아니다. 이력서 여러 버전, 발표 자료, 수료증, 사진, 예전
포트폴리오를 폴더에 모아 둔 사람이 많다. 그래서 로컬 폴더 칸을 함께 둔다.

**경로를 타이핑하게 하지 않는다. 폴더 선택 창을 띄운다.**

Cowork 에는 네이티브 폴더 선택기가 있다(`request_cowork_directory`, 경로 인자를 비우면
로컬 세션에서 창이 뜬다). 폼에서는 폴더가 있는지만 받고, 제출 뒤에 이 창을 띄운다.
경로 오타가 없고, 이 전제의 사용자가 모를 수 있는 경로 복사가 필요 없고, 읽기 권한이
같은 동작에서 승인된다.

폼의 파일 업로드 칸으로 폴더를 받지 않는다. 파일 선택기는 파일 단위이고, 폴더 선택을
붙이면 그 안의 파일이 **전부 대화에 첨부된다.** 아래의 "먼저 목록만 본다"가 그 순간
무너지고, 사용자가 고르기 전에 이미 다 올라가 있게 된다.

폼에 두는 문항은 있는지 없는지 하나다. 이 선택은 자유입력으로 표현되지 않고 에이전트의
행동(창을 띄울지)을 바꾸므로 선택지로 둘 자격이 있다(위 "개수와 분량은 묻지 않는다"의
정당 조건).

읽는 절차가 다른 출처와 다르다. **먼저 목록만 본다.**

1. 폴더를 찾고 파일 **목록**을 읽는다. 내용은 아직 읽지 않는다.
2. 목록을 보여주고 무엇을 읽을지 고르게 한다. 개인 폴더에는 무관한 것과 민감한 것이
   섞여 있고, 그 구분은 사용자만 할 수 있다.
3. 고른 것만 읽는다.

목록 확인 없이 폴더를 통째로 읽지 않는다. 대량 읽기는 되돌릴 수 없고, 클라우드 동기화
폴더라면 읽는 행위 자체가 파일을 내려받아 디스크를 채운다(GUIDE §4.1). 읽기 전에
무엇을 얼마나 내려받게 되는지 말한다.

파일 원문은 워크스페이스에 복사하지 않는다. 다른 출처와 같다. 다만 산출물의 실물
파일(발표 자료, 작품 이미지)은 사용자가 원하면 Artifact 노트 곁으로 옮길 수 있다.
그때는 복사가 아니라 이관이므로 사용자에게 확인받는다.

#### 도구가 없을 때 (흔한 경우다)

**이메일 커넥터는 연결돼 있지 않을 확률이 높다.** 이 전제의 사용자는 Claude 를 질문
답변으로만 써 왔으므로 커넥터를 붙여 본 적이 없다. 그러니 커넥터가 있다고 가정하고
설계하지 않는다.

수집을 시작하기 전에 **가용성을 먼저 확인한다.** 사용자에게 이메일을 보겠다고 말해 놓고
도구가 없어 실패하는 것이 가장 나쁘다. 확인 순서와 대응은 이렇다.

1. 커넥터가 붙어 있으면 그것으로 한다.
2. 없으면 **말하고 고르게 한다.** 연결 방법을 한두 줄로 안내하고(설정에서 커넥터 추가),
   지금은 이메일을 건너뛰고 나머지부터 진행할지 묻는다. 진행 상태에 pending 으로 남겨
   두면 나중에 연결한 뒤 이어서 할 수 있다.
3. **도구를 임의로 갈아타지 않는다.** 커넥터가 없다고 브라우저로 웹메일을 여는 것은
   같은 허락의 범위가 아니다. 사용자가 승인한 것은 "이메일을 본다"가 아니라 특정 경로로
   보는 것이었다. 브라우저로 하려면 허락을 다시 받는다. 민감도가 높은 출처일수록 이
   구분이 중요하다.
4. **조용히 건너뛰지 않는다.** 못 본 출처는 왜 못 봤는지와 함께 보고하고 datasource 에
   `status: 미수집`으로 남긴다. 안 남기면 그 출처는 영원히 없는 것이 된다.

같은 원칙이 Chrome 확장에도 적용된다. 연결이 없으면 그 사실을 말하고 웹 페치로 되는
곳(공개 블로그, 공개 GitHub 프로필)만 처리한 뒤 나머지를 pending 으로 남긴다.

#### 경계

1. **의도적 아카이브만 본다.** 사용자가 남들에게 보이려고 써둔 것과 자기 기록용으로
   모아둔 것이 대상이다. 광고 추적, 브라우징 히스토리, 열려 있는 다른 탭은 대상이 아니다.
2. **출처별로 허락을 받는다.** "인터넷에서 찾아봐도 될까요"는 허락이 아니다. 어느 사이트
   어느 계정인지 단위로 받는다. 이메일은 특히 그렇다.
3. **범위는 좁히되 사용자에게 검색어를 받지 않는다.** 아래 "사전 범위 지정 대신 사후
   필터링" 참조.
4. **제3자 정보는 관계 맥락으로만.** 블로그와 메일에는 남이 나온다. 그 사람을 Person 으로
   만드는 것은 사용자와의 관계가 확인될 때뿐이고, 그 사람 자체의 신상을 수집하지 않는다.
5. **긁은 값은 사실이 아니라 후보다.** 무엇을 뽑을지는 에이전트가 골랐으므로 확인을
   거친다. 출처를 한 줄로 붙여 보여주고 사용자가 확정한 것만 저장한다.
6. **원문을 적재하지 않는다.** 글 전문을 워크스페이스에 복사하지 않는다. 사실만 객체로
   반영하고 원문은 `datasources/` 가 URL 로 가리킨다. 이건 프리셋의 "부적합" 항목이다.

#### 산출

- `datasources/<이름>.md`: 출처마다 하나. URL, 무엇을 뽑았는지, 언제 훑었는지, 다시 볼
  주기. 다음 세션이 증분 수집을 하려면 이 날짜가 필요하다.
- 뽑은 사실은 해당 타입 폴더로 간다. 발표 이력 -> Artifact, 이직 -> Event 와 Organization,
  함께 일한 사람 -> Person.
- 훑었으나 아무것도 못 건진 출처도 datasource 로 남긴다. 빈 결과도 정보다. 안 남기면
  다음 세션이 같은 곳을 또 훑는다.

### R9-b 외부 출처 등록 [MC]

인테이크로 다 못 채운 것을 나중에 어디서 가져올지 등록한다. 이 라운드가 seed 프로파일에도
들어가는 이유는, 여기가 비면 축적이 재개될 실마리가 없기 때문이다.

1. 인덱싱할 출처 (multiSelect): GitHub / 블로그·개인 사이트 / LinkedIn·이력서 / 드라이브 폴더 /
   슬랙·메일 / 없음
2. 각 출처를 어떻게 다룰까: 링크만 등록 / 주기적으로 읽어 반영 / 지금 한 번 읽어 반영

`datasources/<이름>.md` 에 URL, 갱신 주기, 무엇을 뽑을지를 적는다. 원문을 통째로 적재하지 않는다
(프리셋 "부적합" 항목).

### R10 마감 [MC]

1. 어떤 모음을 만들어 둘까 (multiSelect): 경력 타임라인 / 핵심 인물 / 대표 산출물 /
   기술 스택 / 만들지 않음
   - object-sets 는 결과를 박지 않고 **필터 명세**로 적는다. 그래야 스테일해지지 않는다.
2. 앞으로 새 사실이 나오면: 물어보지 말고 바로 기록 (권장) / 매번 확인받기
   - 답을 `memory/` 에 사용자 선호로 남긴다. GUIDE §12 능동적 축적의 강도 설정이다.

마감에서 에이전트가 하는 일: object-sets/object-views 생성, [[personal-rag-lint]] 실행,
`_project.md` 와 `memory/MEMORY.md` 갱신, action-log 엔트리, 그리고 **채워진 것과 빈 것의 요약**을
사용자에게 보고한다. 빈 라운드 목록이 다음 세션의 재개 지점이 된다.

## 답변 -> 파일 매핑

| 라운드 | 쓰는 파일 | 쓰는 방식 |
|---|---|---|
| R0 | `memory/personal-rag-intake.md`, `_project.md` | 프로파일과 공개 범위를 상태로 기록 |
| R1 | `objects/people/<이름>.md` | 기존 루트 노트 갱신 (rewrite) |
| R2 | `objects/organizations/<이름>.md` n개 + 루트 `links.worksAt` | 신규 + 루트 갱신 |
| R3 | `objects/projects/<slug>.md` n개 | 신규. 루트에 `participatedIn` |
| R4 | `objects/people/<이름>.md` n개 | 신규. 루트에 `knows`/`familyOf`/`colleagueOf` |
| R5 | `objects/events/<slug>.md` n개 | 신규. `involvesPerson` 으로 루트 연결 |
| R6 | `objects/places/<이름>.md` n개 | 신규. 기존 노트의 지명 문자열을 위키링크로 교체 |
| R7 | `objects/ideas/<이름>.md` n개 | 신규. 루트에 `hasSkill`/`interestedIn`/`believes` |
| R8 | `objects/artifacts/<slug>.md` n개 | 신규. `createdBy` 루트, `partOf` 프로젝트 |
| R9 | `datasources/<이름>.md` n개 | 신규 |
| R10 | `object-sets/*`, `object-views/*`, `memory/MEMORY.md`, `action-log/<YYYY-MM-DD>.md` | 신규 + 인덱스 갱신 |

쓰기는 전부 GUIDE §6 쓰기 프로토콜을 탄다. 템플릿은 `templates/<타입>.md.tpl` 를 쓰고
빈 필드는 지우지 말고 빈 채로 남긴다. 나중에 무엇이 비었는지가 다음 질문거리다.

## 중단과 재개

인테이크는 중간에 끊기는 것이 정상이다. 진행 상태는 memory-layer 사실(in-flight status)이므로
`memory/personal-rag-intake.md` 에 둔다. 개념 폴더에 두지 않는다. 프로토콜의 메모리
라우팅 규칙상 `memory/` 는 LLM 메모리 레이어(정체성·선호·피드백·진행 상태)이고 큐레이션
지식이 아니다.

```yaml
---
type: document
title: personal-rag 인테이크 진행 상태
profile: standard
visibility: private
updated: 2026-08-19
---

| 라운드 | 상태 | 비고 |
|---|---|---|
| R0 | done | standard, 비공개 |
| R1 | done | |
| R2 | partial | 과거 소속 미기록 |
| R3 | skipped | 사용자가 나중으로 미룸 |
| R4~R10 | pending | |
```

`memory/MEMORY.md` 에 인덱스 한 줄을 넣는다. 다음 세션에서 이 줄이 재개 지점을 알려준다.
전 라운드가 done 이면 이 파일을 지우지 말고 `completed` 로 상태만 바꾼다. 언제 무엇을
물었는지가 나중에 "왜 이 필드가 비었나"의 답이 된다.

## 안티패턴

| 하면 안 되는 것 | 왜 |
|---|---|
| 10문항을 한 번에 던지기 | 도구 한계 4문항. 넘기면 잘리고, 사용자도 이탈한다 |
| 탈출구 없는 강제 선택 | 없는 사실이 만들어진다. 오염이 구조보다 오래 남는다 |
| 이름만 있는 객체 대량 생성 | 링크 없는 노드는 조회에 안 잡히고 lint 만 시끄럽다 |
| 답을 다 모은 뒤 한 번에 쓰기 | 중단되면 전부 날아간다 |
| 빈 프로퍼티를 추론으로 채우기 | 근거 없는 값이 근거 있는 값과 구분 불가해진다 |
| 추측한 값을 폼에 미리 채우기 | 남이 쓰다 만 폼이 된다. 앵커링 + 출처 소실 + 불투명 |
| 사용자에게 해당할 법한 값을 placeholder 로 쓰기 | 위와 같은 문제가 회색 글씨로 일어난다 |
| 개수·분량 선택지 + 자유입력 칸 조합 | 선택이 입력을 구속하지 못한다. 적은 개수가 곧 답이다 |
| 허락을 선택지로 만들기 | "연도만 적어도 된다"는 라벨 한 줄이면 된다. 선택지는 제약처럼 읽힌다 |
| 민감 항목을 선제적으로 묻기 | 프로토콜의 민감정보 규칙은 사용자 지시가 전제다 |
| 사용자 답을 임의 kind 에 배정 | kind 는 조회 축이다. 애매하면 되묻는다 |
| 7종에 억지로 끼워맞추기 | 새 타입을 만든다([[personal-rag-object-types]]) |

## 완료 판정

인테이크가 끝났다고 말할 수 있는 조건. 라운드를 다 돈 것과 다르다.

1. 루트 Person 이 `name` 과 링크 3개 이상을 갖는다.
2. 루트에서 위키링크 2홉으로 닿는 객체가 5개 이상이다. (그래프가 연결됐다는 뜻)
3. 고아 객체가 없다. 어떤 인스턴스도 링크 0 이 아니다.
4. 모든 위키링크가 실재 노트를 가리킨다(규칙 9).
5. `datasources/` 가 비어 있지 않거나, R9 에서 "없음"이 명시적으로 선택됐다.
6. `memory/personal-rag-intake.md` 의 모든 라운드가 done / skipped 로 판정돼 있다.
   pending 이 남아 있으면 완료가 아니라 중단이다.

2번이 안 되면 객체는 있는데 그래프가 아니다. 그 상태에서 "이 사람에 대해" 질의하면 개별 파일
grep 과 다를 바 없어진다. 이 프리셋의 존재 이유가 링크이므로 2번을 통과 못 하면 R4~R7 을 더 돈다.
