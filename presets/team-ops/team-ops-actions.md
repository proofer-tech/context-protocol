# 액션 어휘와 로그 형식

Foundry 의 Action Type 은 객체 데이터를 통제된 방식으로 바꾸는 단위다. 단순 편집이
아니라 "어떤 의도의 변경인가"를 의미적으로 남긴다. 이 프리셋은 그 어휘를 프로토콜의
action-log 스트림(GUIDE §12.3, [[action-log]])에 얹는다.

프리셋은 로그의 **시간축 규칙을 바꾸지 않는다**. 하루 한 파일(`action-log/2026-09-10.md`),
append 전용, 상대시간 금지는 전부 프로토콜 소관이다. 프리셋이 더하는 것은 "무엇을
했다"를 부르는 이름 8개와 엔트리 한 줄의 내부 형식뿐이다.

팀 워크스페이스에서 이 로그가 개인 워크스페이스보다 값이 크다. 노트 본문은 현재 상태만
담고 이전 값을 잃는데, 팀에서는 "언제 누가 이 값을 바꿨나"가 실제 조회 질문이기 때문
이다. 노트가 무엇인지를 답하고 로그가 언제부터인지를 답한다.

## 액션 타입 8종

| 액션 | 파라미터 | 사이드 이펙트 |
|---|---|---|
| `createObject` | objectType, primaryKey, initialProperties | 없음 |
| `updateProperty` | target, field, from, to | 이전 값 보존(로그에 from 기록) |
| `addLink` | subject, predicate, object | 양쪽 중 정본 한쪽에만 기록 |
| `removeLink` | subject, predicate, object | 링크 해제 |
| `recordDecision` | slug, title, decidedAt, decidedBy, affects | createObject:Decision, 링크 decidedBy·affects |
| `supersedeDecision` | oldDecision, newDecision, reason | 새 결정에 supersedes, 옛 결정 status 를 superseded 로 |
| `recordIncident` | slug, severity, startedAt, affects, owner | createObject:Incident, 링크 affects |
| `closeInitiative` | target, endDate, status, outcome | status 를 done 또는 abandoned 로, outcome 기록 |

앞의 넷은 [[personal-rag-actions]] 와 같다. 뒤의 넷이 이 프리셋 고유이고, 전부 **여러
파일을 한 의도로 묶는 것**이 존재 이유다. 결정 하나를 남기려면 최소 두 파일을 건드리는데
그것이 로그에 두 줄로 흩어지면 나중에 둘이 한 사건이었는지 알 수 없다.

### createObject

새 인스턴스를 등록한다. 검증: 같은 폴더에 동일 PK 가 있으면 거부하고 `updateProperty`
로 처리한다. 해당 타입의 필수 프로퍼티가 다 채워져 있어야 한다. Owned 구현 타입이면
`owner` 가 Team 인지 확인한다(규칙 13).

Decision 과 Incident 는 이 액션으로 만들지 않고 아래 전용 액션을 쓴다. 링크가 함께
서지 않은 결정과 장애는 만들자마자 고아가 된다.

### recordDecision

한 액션으로 Decision 객체를 만들고 참여자와 영향 대상까지 연결한다. `context` 와
`rationale` 이 비어 있으면 거부한다(규칙 15). 결론만 있는 결정 노트는 티켓 제목과
다를 바 없고, 나중에 채우겠다는 약속은 지켜지지 않는다.

로그에는 recordDecision 한 줄로 남기고, 갱신 원본에 Decision 노트와 링크가 붙은 노트
경로를 함께 적는다.

### supersedeDecision

결정을 뒤집는다. 세 가지가 한 동작이다. 새 Decision 생성 또는 지정, 새 쪽에
`supersedes` 기재, 옛 쪽 `status` 를 `superseded` 로 변경. 셋 중 하나라도 빠지면
규칙 14 위반 상태가 남는다.

**옛 결정을 지우지 않는다.** 뒤집힌 결정은 "왜 지금 이렇게 하는가"의 절반이다. 과거에
무엇을 시도했고 왜 접었는지가 사라지면 같은 제안이 반년마다 돌아온다.

방향만 틀렸고 대체안이 없으면 `reverted` 다. 이 액션이 아니라 `updateProperty` 로
status 를 바꾸고 이유를 본문에 적는다. 두 상태의 차이는 [[team-ops-schema]] 에 있다.

### recordIncident

장애를 등록하고 영향받은 System 에 연결한다. 대응 중에 쓰이므로 `resolvedAt` 은 비운
채로 시작하고, 복구 시 `updateProperty` 로 채운다. `detectedAt` 을 `startedAt` 과 같은
값으로 채우지 않는다. 모르면 비운다. 같은 값을 넣으면 관측 지연이 0 으로 집계된다.

회고에서 나온 파생물은 이 액션이 아니라 `addLink triggers` 로 붙인다. 파생물이 하나도
없는 복구된 sev1 은 lint 경고 대상이다(규칙 18).

### closeInitiative

이니셔티브를 닫는다. `status` 를 `done` 또는 `abandoned` 로 바꾸고 `endDate` 와
`outcome` 을 기록한다. **`outcome` 없이 닫지 않는다.** 특히 `abandoned` 가 그렇다.
접은 시도가 가장 자주 다시 제안되고, 왜 접었는지가 없으면 그 제안을 막을 근거가 없다.

닫아도 삭제하지 않는다. 이 프리셋은 객체를 삭제하지 않는다. 이니셔티브가 닫혀도
`guidedBy` 로 걸린 Decision 은 계속 유효하다는 점을 기억한다([[team-ops]] 의
Decision 과 Initiative 구분).

## 엔트리 형식

프로토콜의 엔트리 골격(무엇 / 갱신 원본 / 출처 / 확인)을 유지하고, "무엇" 한 줄 안에 액션
타입과 대상을 앞세운다.

```
## 2026-09-10
- 무엇: recordDecision [[주-저장소로-포스트그레스를-쓴다]] - 몽고 운영 부담과 조인 요구
  - 갱신 원본: objects/decisions/주-저장소로-포스트그레스를-쓴다.md,
    objects/systems/주-저장소.md
  - 출처: 2026-09-08 아키텍처 리뷰 (참석 4인)
  - 확인: 직접 확인
- 무엇: supersedeDecision [[배포는-목요일에-하지-않는다]] -> [[배포는-언제든-한다]]
  - 갱신 원본: objects/decisions/배포는-언제든-한다.md,
    objects/decisions/배포는-목요일에-하지-않는다.md
  - 출처: 2026-09-09 회고
  - 확인: 보고됨(회고 진행자)
- 무엇: updateProperty [[결제-게이트웨이]].tier important -> critical
  - 갱신 원본: objects/systems/결제-게이트웨이.md
  - 출처: [[2026-08-결제-지연]] 회고 액션
  - 확인: 직접 확인
- 무엇: closeInitiative [[결제-스트라이프-이관]] abandoned - 수수료 재협상으로 불필요해짐
  - 갱신 원본: objects/initiatives/결제-스트라이프-이관.md
  - 출처: 2026-09-10 스탠드업
  - 확인: 보고됨(이니셔티브 담당자)
```

규칙:
- 액션 타입은 표의 8개 이름 그대로 쓴다. 임의 동사를 쓰면 로그가 grep 되지 않는다.
- `updateProperty` 는 `대상.필드 이전 -> 이후` 형태로 이전 값을 남긴다. 원본에서는
  값이 덮어써지므로 로그가 유일한 이력이다.
- 대상은 위키링크로 적어 객체와 로그가 서로 도달 가능하게 한다.
- 상대 시간은 절대 날짜로 변환한다.
- **출처에 회의명이나 채널을 적는다.** 개인 워크스페이스에서는 출처가 대개 "사용자
  발화" 하나였지만, 팀에서는 같은 사실을 서로 다른 자리에서 들은 두 사람이 다르게 적을
  수 있다. 어느 자리에서 나온 말인지가 충돌 판정의 근거다.
- 1인칭을 쓰지 않는다. 로그 본문도 규칙 16 대상이다.

## Decision 으로 승격하는 기준

모든 합의가 Decision 이 되지는 않는다. 로그는 변경의 흔적이고 Decision 은 이후 팀의
행동을 구속하는 규범이다. 슬랙에서 30초 만에 정한 것을 전부 Decision 으로 만들면
`objects/decisions/` 가 잡음으로 차고, 정작 중요한 결정이 그 안에 묻힌다. 반대로
아무것도 승격하지 않으면 반년 뒤 아무도 이유를 모른다. 경계는 다음 넷 중 하나다.

- **되돌리는 데 비용이 든다.** `reversible` 이 hard 또는 oneWay 면 무조건 승격한다.
  쉽게 되돌릴 수 있는 것은 되돌리면 되고 기록할 것이 없다.
- **뒤에 온 사람이 왜냐고 물을 것이다.** 지금은 자명하지만 맥락이 사라지면 이상해
  보이는 것. 목요일 배포 금지, 특정 라이브러리 금지, 리뷰어 2인 규칙이 그렇다.
- **다른 선택지가 실제로 검토됐다.** 대안을 놓고 비교한 흔적이 있으면 그 비교가 자산
  이다. 대안이 하나뿐이었으면 결정이 아니라 사실이다.
- **어긴 것을 지적할 일이 생긴다.** 규범으로 작동할 것이면 어딘가에 적혀 있어야 한다.
  적히지 않은 규범을 근거로 남을 지적하는 것이 팀에서 가장 나쁜 형태다.

승격하지 않는 예: 변수명 합의, 이번 스프린트 담당 분배, 회의 시간 조정, 이미 정해진
방침을 한 번 적용한 것. 로그 한 줄이나 해당 객체의 프로퍼티 변경으로 끝낸다.

애매하면 승격한다. 안 쓰이는 Decision 노트의 비용은 파일 하나이고, 없는 Decision 의
비용은 같은 논의를 다시 하는 것이다. 다만 `context` 와 `rationale` 을 못 적겠으면
그것은 승격 대상이 아니라는 신호다. 적을 것이 없다는 뜻이기 때문이다.

승격 판단은 에이전트가 하고 사용자에게 매번 묻지 않는다. 물어야 할 때는 결정 참여자가
누구였는지가 불분명할 때뿐이다.

## 여러 사람이 같은 로그 파일에 append 한다는 조건

하루 한 파일 규칙은 프로토콜 소관이라 바꾸지 않는다. 그런데 팀에서는 그 하루 파일에
여러 세션이 각자 붙는다. 두 에이전트 세션이 같은 파일을 같은 시각에 열면 나중에 쓴
쪽이 앞선 쪽의 엔트리를 통째로 지운다. 마운트가 잠금을 제공하지 않으므로 규율로 막는다.

**1. append 만 한다. rewrite 하지 않는다.** 오늘 날짜 파일에 대해 `write_file` 의
rewrite 모드를 쓰지 않는다. 읽어서 고쳐 쓰는 순간 그 사이에 들어온 남의 엔트리가
사라진다. 오타를 발견해도 위쪽 엔트리를 수정하지 말고 아래에 정정 엔트리를 붙인다.

**2. 쓰기 직전에 다시 읽는다.** 세션 시작 때 읽은 내용은 이미 낡았을 수 있다. append
직전에 파일 끝을 확인하고, 방금 쓰려던 것과 같은 엔트리가 이미 있으면 쓰지 않는다.
두 사람이 같은 회의를 각자 기록하는 상황이 실제로 자주 일어난다.

**3. 엔트리는 한 액션으로 끝낸다.** 한 액션의 네 줄(무엇 / 갱신 원본 / 출처 / 확인)이 한 번의
append 로 들어가야 한다. 나눠 쓰면 그 사이에 남의 엔트리가 끼어들어 소속이 뒤섞인다.

**4. 중복은 지우지 말고 합친다.** 같은 사실이 두 번 기록됐으면 뒤엣것에 "앞 엔트리와
같은 건"이라고 붙인다. 지우는 것이 append 전용 원칙을 깨는 것보다 낫지 않다. 로그가
조금 지저분한 것은 로그가 유실되는 것보다 훨씬 싸다.

**5. 하루 파일을 사람별로 쪼개지 않는다.** `2026-09-10-민수.md` 같은 분할은 충돌을
없애지만 시간순 읽기를 파괴한다. 로그의 값은 한 줄로 이어지는 시간축이고, 그것을 잃으면
로그가 아니라 개인 메모 더미가 된다. 충돌은 위 넷으로 막는다.

## 능동적 축적과의 접점

GUIDE §12.1 트리거가 발화하면 §12.2 라우팅으로 갈린다. 이 프리셋을 쓰는 워크스페이스
에서 라우팅은 이렇게 구체화된다.

- 새 사람, 시스템, 이니셔티브, 지표 등장 -> `objects/<type>/` 에 인스턴스 생성
  (createObject) + 로그 한 줄.
- 팀이 무언가를 정함 -> 위 승격 기준으로 판정. 승격이면 recordDecision, 아니면 해당
  객체의 updateProperty + 로그 한 줄.
- 기존 결정을 뒤집음 -> supersedeDecision. 옛 노트를 지우지 않는다.
- 장애 발생 -> recordIncident. 복구 시 updateProperty, 회고 시 addLink triggers.
- 일이 끝나거나 접힘 -> closeInitiative. outcome 필수.
- 관계가 새로 드러남 -> 정본 쪽 노트에 링크 추가(addLink) + 로그 한 줄. 정본 방향은
  [[team-ops-schema]] 의 술어 표에 있다.
- 사람이 팀을 떠남 -> Person 의 `leftAt` 과 `kind: alumni`, 그리고 그 사람에게 걸린
  `oncall` 을 찾아 옮긴다. 이 두 번째를 빼먹는 것이 이 프리셋에서 가장 흔한 사고다.
- 사용자 개인의 선호나 세션 진행 상태 -> `memory/` (객체가 아니다).
- 큐레이션이 바뀔 만한 변경 -> 같은 작업에서 관련 `object-sets/`, `object-views/`
  갱신. 라이브 뷰가 없으니 이 단계를 빠뜨리면 뷰가 스테일해진다.
