# 조직 도입 가이드

회사나 기관이 context-protocol 을 사내 지식의 SoT(1차 정보원)로 도입할지 검토할 때 보는 문서다.
프로토콜이 무엇을 보장하고 무엇을 보장하지 않는지, 보장하지 않는 부분을 조직이 어떻게 채우는지를
적는다. 개인이나 비영리 용도라면 [설치 가이드](설치-가이드.md) 로 충분하다.

## 1. 라이센스

`LICENSE` 의 두 라이센스 중 하나를 골라 쓴다. 아래 표는 요약이고, 효력은 원문(`LICENSES/`)에만 있다.

| 쓰임 | 근거 |
|---|---|
| 개인, 연구, 학습, 학교, 공공기관, 비영리 단체 | PolyForm Noncommercial 1.0.0 |
| 영리 기업의 사내 업무 (사내 SoT, 직원과 사내 에이전트용 컨텍스트, 사내 평가와 PoC, 사내 수정) | PolyForm Internal Use 1.0.0 |
| 고객사에 설치해 주거나 납품물에 포함, 호스팅 서비스로 제공, 유료 교육이나 컨설팅 상품에 포함, 판매 | 별도 상업 라이센스 |

Internal Use 는 사내에서 쓰고 고치는 것을 허용하지만 회사 밖으로 배포하는 것은 허용하지 않는다.
같은 회사와 지배 관계에 있는 계열사는 "your company" 에 포함된다(원문 Definitions). 판단이 서지 않으면
[이슈](https://github.com/proofer-tech/context-protocol/issues) 로 쓰임을 적어 문의한다.

## 2. 책임 경계: 프로토콜이 하는 것과 하지 않는 것

context-protocol 은 **에이전트가 지키는 규약**이다. 파일을 어디에 어떤 모양으로 두는지, 무엇을 먼저
읽는지, 언제 무엇을 기록하는지를 정한다. 접근 통제, 트랜잭션, 감사 같은 강제력은 규약이 아니라
그 아래의 저장소와 실행 환경이 가진다. 조직 도입에서는 이 경계를 먼저 분명히 해야 한다.

| 영역 | 프로토콜이 하는 것 | 조직이 맡는 것 |
|---|---|---|
| 접근 통제 | 공개(L1a)와 비공개(L1b) 워크스페이스를 나누고, 민감 정보는 비공개에만 두며 공개 쪽에서 가리키지도 않게 한다 | 두 워크스페이스를 권한이 다른 저장소나 드라이브에 둔다. SSO, 부서별 RBAC, 접근 감사 |
| 외부 전송 | 없음. 에이전트가 읽은 내용은 그 하네스의 모델로 간다 | 승인한 하네스와 모델만 쓰게 하는 정책, 데이터 처리 계약, DLP |
| 비밀 정보 | 없음. 민감 정보는 비공개 워크스페이스에 두라는 규칙뿐이다 | 비밀 스캔(pre-commit, 저장소 스캔) |
| 동시 수정 | 쓰기 전에 다시 읽고, 날짜가 어긋나면 병합한다. `git` 백엔드(8.3)에서는 받기, 요청 단위 커밋, 충돌 해소 범위까지 정한다 | 원격 저장소의 브랜치 보호와 쓰기 소유권(CODEOWNERS) |
| 최신성 | `grounded_on` 과 근거 drift 신호, `supersedes` 로 유효한 판 결정, 프리셋의 효력 기간 필드 | 원본 변경 감지와 재검증 주기, 만료 자료 차단 규칙 채택 |
| 기록 승인 | 확정/제안 절 구분. `git` 백엔드의 승인반영(`review`)에서는 에이전트가 브랜치와 PR 까지만 하고 병합하지 않는다 | 누가 병합할지, 어느 폴더를 승인반영으로 둘지 |
| 신뢰 등급 | 선택 키 `trust_tier`(8.3). 확인 안 된 문서로 답할 때 밝히고, 정리 노트가 근거보다 높은 등급을 달면 린트 신호 | 어떤 문서를 `verified` 로 올릴지 정하는 담당 |
| 규칙 준수 | 무결성 규칙과 실행 가능한 린트 | 린트를 CI 에 걸어 병합 전에 막는다 |

## 3. 권장 구성

### 저장 위치

- **개인 드라이브에 두지 않는다.** 회사 공유 드라이브(`gdrive` 백엔드)나 사내 git 서버의 저장소를 쓴다.
- 감사와 승인이 중요하면 **사내 git 저장소**가 낫다. 각자 로컬에 clone 하고 설치할 때 백엔드로 `git` 을
  고른다(8.3). 이력, PR 승인, 브랜치 보호, CODEOWNERS 를 그대로 쓰고, 에이전트는 반영 모드에 따라
  기본 브랜치에 바로 올리거나(`direct`) 브랜치와 PR 까지만 만든다(`review`). 기본값은 `review`,
  `memory/` 와 `action-log/` 만 `direct` 로 두는 구성을 권한다. 절차는 `_context-protocol/backends/git.md`.
- git 저장소를 클라우드 동기화 폴더(Drive 등) 안에 두지 않는다. 동기화가 `.git` 을 깨뜨릴 수 있다.
- 공개와 비공개를 **서로 다른 저장소**로 나눈다. 폴더 하나 안의 구분은 권한 경계가 아니다.

### 에이전트 실행 환경

- 조직이 승인한 하네스만 쓴다. 지원 하네스와 각자의 진입 파일, 파일 도구는
  `_context-protocol/harnesses/` 의 프로파일에 있다.
- 하네스의 데이터 정책(학습 사용 여부, 보존 기간)과 모델 제공자 계약을 조직 기준으로 확인한다.

## 4. 운용 규칙 예시

아래는 워크스페이스 루트 `CONTEXT.md` 에 조직 규칙으로 덧붙이는 예시다. `CONTEXT.md` 는 워크스페이스가
가진 파일이라 이렇게 덧붙여도 마이그레이션이 덮어쓰지 않는다. 포털(`AGENTS.md`, `CLAUDE.md`)에는
적지 않는다.

### 공식 정본은 승인을 거쳐서만 바뀐다

`git` 백엔드를 쓰면 이 규칙은 `CONTEXT.md` frontmatter 의 반영 모드로 대신한다.

```yaml
git_merge: review
git_merge_paths:
  memory/: direct
  action-log/: direct
```

git 을 쓰지 않는 워크스페이스(공유 드라이브 등)라면 아래 규칙을 덧붙인다.

```markdown
11. 조직 규칙: 공식 정본 폴더(`policies/`, `decisions/`)의 파일은 직접 고치지 않는다.
    바꿀 내용은 새 브랜치에서 고치고 PR 로 올린다. 담당자가 병합하기 전까지 그 내용은
    사실이 아니라 제안이다. 대화에서 나온 새 사실은 제안 절(`## 제안 (미확정)`)에 둔다.
    item 4 의 능동 축적은 이 두 폴더 밖에서만 직접 쓴다.
```

team-ops 프리셋을 쓰면 Decision 의 `status: proposed` 와 `accepted` 가 같은 구분을 객체 단위로 준다.

### 만료된 자료로 답하지 않는다

먼저 효력 종료일 키를 정한다. compliance 프리셋을 쓰면 `effectiveTo` 가 이미 있다. 코어 문서에도
쓰려면 `_context-protocol/_schema/concept-scheme.md` 에 `valid_until` 같은 키를 먼저 등재한다
(`_ontology.md` "어휘를 늘릴 때"). 그다음 규칙을 덧붙인다.

```markdown
12. 조직 규칙: `valid_until` 이나 `effectiveTo` 가 오늘보다 이른 문서를 근거로 답하지 않는다.
    그런 문서밖에 없으면 "만료된 자료뿐" 이라고 밝히고 담당자를 안내한다. `supersedes` 로
    대체된 판도 근거로 쓰지 않는다.
```

### 근거 원본을 주기적으로 대조한다

`grounded_on` 으로 원본을 이은 정리 노트는 원본이 바뀌면 근거 drift 신호가 뜬다. 아래 CI 를 주 1회
돌리고, 신호가 뜬 노트는 담당자가 원본과 대조해 고치거나 `grounded_checked` 를 갱신한다.

## 5. 린트를 CI 에 건다

규칙을 에이전트가 지키는지에 기대지 않으려면 `_context-protocol/tools/integrity_lint.py` 를 CI 에서
돌린다. 표준 라이브러리만 쓰고(PyYAML 이 있으면 쓴다), 규칙 위반이 있으면 종료 코드 1 이다.

| 결과 | 뜻 |
|---|---|
| 규칙 1~6 위반 | broader 누락, 끊어진 링크, 소속 없는 문서, broader 순환, top concept 오류, `_project.md` 의 미해결 주제. 병합을 막는다 |
| 검토 신호 | 분해 검토, 근거 drift, 효력 만료. 기본은 통과로 치고 `--signals-fail` 을 주면 실패로 친다 |

사내 워크스페이스 저장소의 GitHub Actions 예시:

```yaml
name: workspace-lint
on:
  pull_request:
  schedule:
    - cron: "17 0 * * 1"   # 매주 월요일. 근거 drift 와 효력 만료를 주기적으로 본다
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install pyyaml
      - run: python3 _context-protocol/tools/integrity_lint.py .
      - if: github.event_name == 'schedule'
        run: python3 _context-protocol/tools/integrity_lint.py . --signals-fail
```

근거 drift 는 파일 수정 시각으로 판정하므로, git checkout 직후에는 모든 파일의 수정 시각이 같아져
신호가 덜 뜬다. 정확히 보려면 사내 문서 원본을 같은 저장소가 아닌 원래 자리(공유 드라이브 등)에서
대조하는 절차를 함께 둔다.

## 6. 사내 시스템과의 관계

워크스페이스는 검증된 지식의 1차 정보원(L1)이고, Notion, Confluence, Slack, 이슈 트래커는 휘발성
사실을 조회하는 라이브 소스(L3)다. 에이전트는 워크스페이스를 먼저 보고, 없거나 휘발성 사실일 때만
라이브 소스를 조회한다(가이드 2절, 3절). 라이브 소스는 하네스의 커넥터(MCP 등)로 붙인다. 라이브 소스에서
확인한 결정을 워크스페이스로 옮길 때는 4절의 승인 규칙을 따른다.

## 7. 검토할 때 알아 둘 것

- **성숙도.** 공개 저장소는 2026-11 에 열었지만 프로토콜은 2026-08 의 첫 배포 패키지(5.0)부터 여러
  워크스페이스에서 운용하며 8.4 까지 올라왔다. 버전별 변경은 [CHANGELOG](../CHANGELOG.md), 각 버전을 기존 워크스페이스에
  적용하는 델타는 `CONTEXT_MIGRATE.md` 의 버전 레지스트리에 있다.
- **규칙이 길다.** 에이전트가 규칙을 덜 지키면 구조가 흐트러진다. 5절의 CI 가 그 하한을 잡는다.
- **조직 기능의 범위.** 승인반영과 git 기반 동시 수정은 8.3 의 `git` 백엔드가, 신뢰 등급은 `trust_tier`
  가 맡는다. 둘 다 고르지 않은 워크스페이스는 8.2 와 똑같이 동작한다. 효력 기간은 아직 코어 키가 아니고
  4절처럼 프리셋 필드나 워크스페이스 어휘로 구성한다. `git` 백엔드의 세션 절차는 여러 하네스에서
  실측되기 전이다.
