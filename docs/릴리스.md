# 릴리스 절차

설치 패키지(zip)는 저장소에 커밋하지 않는다. **GitHub Release 로만 배포한다.** 저장소에는
패키지를 만드는 재료인 정본만 있다.

## 저장소와 프로토콜 워크스페이스

유지보수자의 프로토콜 워크스페이스(구글 드라이브의 `context-protocol` 폴더)가 **이 저장소의 작업
트리**다. 그 폴더에서 세션들이 규칙을 따르며 결함을 찾고 정본을 고치고, 그대로 커밋한다. 예전에 그
폴더의 `dist/` 에 쌓던 zip 은 이제 GitHub Release 가 대신한다.

그 워크스페이스에만 있는 기록(`memory/`, `action-log/`, `fleet/`, `references/`, 루트
`CONTEXT.md`/`AGENTS.md`/`CLAUDE.md`/`_project.md`, `_context-protocol/_concepts/`,
`_context-protocol/_deprecated_v5/`, `dist/`)은 `.gitignore` 로 빠져 있고 공개되지 않는다.

**git 은 호스트에서 직접 돌린다.** 클라우드 동기화 폴더 위의 git 은 잠금 파일을 만들고 지우므로,
삭제가 막힌 환경(Cowork 연결 폴더)에서는 깨진다. Mac 터미널이나 Mac 에서 직접 실행한 에이전트에서
돌리거나, 삭제 권한을 받은 뒤에 돌린다. 커밋 직후 Drive 동기화가 끝나기 전에 다른 PC 에서 같은
폴더로 git 을 돌리지 않는다.

## 버전과 태그

| 경우 | 태그 | zip 이름 |
|---|---|---|
| 프로토콜 버전이 올라갔다 | `v<버전>` | `context-protocol-<버전>.zip` |
| 버전은 그대로, 패키지만 고쳤다 (README 문구, 프리셋 추가 등) | `v<버전>-b<N>` | `context-protocol-<버전>-b<N>.zip` |

- 버전은 `CONTEXT_MIGRATE.md` 의 LATEST_VERSION 이다. 임의로 정하지 않는다.
- 같은 이름으로 다시 올리지 않는다. 한 번 배포한 zip 의 해시가 바뀌면 어떤 패키지로 설치된
  워크스페이스인지 되짚을 수 없다. 워크플로도 이미 붙은 zip 을 덮어쓰지 않는다.
- `latest` 같은 별칭 파일을 두지 않는다. 옛 Release 는 지우지 않는다.

## 절차

`scripts/build.sh` 는 스테이징을 임시 디렉토리에 만들고 결과만 `dist/` 에 둔다.

1. **정본을 고치고 커밋한다.** `_context-protocol/` 와 `presets/` 를 고친다. 설치기 블록도 같이 고친다.
2. **패키지 README 를 맞춘다.** `package/README.md` 의 제목과 `- 버전:` 줄, 설치 후 확인 항목,
   수록 프리셋 목록을 이번 버전에 맞춘다.
3. **빌드로 검증한다.** `scripts/build.sh [빌드번호]`. 아래를 모두 통과해야 다음으로 간다.
   - 설치기 두 개와 가이드의 `Guide version:` 이 LATEST_VERSION 과 같다
   - 패키지 README 의 버전 표기가 같다
   - 설치기 블록(`<guide_content>`, `<ontology_readme>` 등)이 정본 파일과 일치한다
   - 압축을 풀어 스테이징과 `diff -r` 했을 때 차이가 없다
4. **커밋하고 태그를 push 한다.**

   ```bash
   git add -A && git commit -m "8.3: <바뀐 것 한 줄>"
   git push
   git tag v8.3 && git push origin v8.3
   ```

   태그를 push 할 수 없는 환경이면 Actions 탭에서 `release` 워크플로를 수동 실행하고 태그 이름
   (`v8.3`)을 입력한다. 워크플로가 main 의 그 커밋에 태그와 Release 를 함께 만든다.

   ```bash
   gh workflow run release.yml -f tag=v8.3
   ```

5. **Release 를 확인한다.** `release` 워크플로가 같은 빌드를 돌려 zip 을 Release 에 붙인다.
   Release 노트에 바뀐 것과 zip 의 sha256 을 적는다. 해시는 워크플로 로그의 마지막 줄에 있다.
6. **워크스페이스에 기록한다.** `dist/protocol-build.md` 빌드 이력에 한 줄(버전, 빌드, 날짜,
   sha256 앞 16자, 비고)과 `action-log` 엔트리. 둘 다 `.gitignore` 대상이다.

## 워크플로 없이 올릴 때

이미 검증한 zip 을 그대로 올려야 할 때는 직접 만든다.

```bash
gh release create v8.3 dist/context-protocol-8.3.zip --title "context-protocol 8.3" --notes-file notes.md
```

워크플로가 그 뒤에 같은 태그로 돌아도 같은 이름의 zip 이 이미 있으면 건너뛴다.

## 저장소 이전의 빌드

8.2 까지의 패키지는 저장소가 생기기 전에 프로토콜 워크스페이스의 `dist/` 에서 빌드됐다. 그 zip 들은
Release 에 없다. 저장소의 첫 Release 는 같은 8.2 정본을 이 저장소의 스크립트로 다시 빌드한
`v8.2-b2` 다. 내용은 워크스페이스의 8.2 빌드와 같고 MANIFEST 의 빌드 표기와 날짜만 다르다.
