# 릴리스 절차

설치 패키지(zip)는 저장소에 커밋하지 않는다. **GitHub Release 로만 배포한다.** 저장소에는
패키지를 만드는 재료인 정본만 있다.

## 정본이 두 곳에 있는 이유와 방향

프로토콜은 원래 하나의 프로토콜 워크스페이스(유지보수자의 구글 드라이브 폴더)에서 작성되고
운용된다. 그곳의 세션들이 실제로 규칙을 따르면서 결함을 찾고 고친다. 이 저장소는 그 정본을
공개하는 자리다.

- **작성은 프로토콜 워크스페이스에서 한다.** 고친 정본은 릴리스할 때 이 저장소로 옮긴다.
- **저장소로 들어온 기여(PR)는** 병합한 뒤 프로토콜 워크스페이스에 같은 변경을 반영한다.
- 둘이 어긋난 채로 태그를 찍지 않는다. 아래 2단계의 대조가 그것을 막는다.

워크스페이스에서 저장소로 옮기지 않는 것: `memory/`, `action-log/`, `fleet/`, `references/`,
`_project.md`, 루트 `CONTEXT.md`/`AGENTS.md`/`CLAUDE.md` (그 워크스페이스의 설치본이다),
`_context-protocol/_concepts/` (설치기가 대상 폴더에 새로 만드는 인스턴스다),
`_context-protocol/_deprecated_v5/`, `dist/`.

## 버전과 태그

| 경우 | 태그 | zip 이름 |
|---|---|---|
| 프로토콜 버전이 올라갔다 | `v<버전>` | `context-protocol-<버전>.zip` |
| 버전은 그대로, 패키지만 고쳤다 (README 문구, 프리셋 추가 등) | `v<버전>-b<N>` | `context-protocol-<버전>-b<N>.zip` |

- 버전은 `CONTEXT_MIGRATE.md` 의 LATEST_VERSION 이다. 임의로 정하지 않는다.
- 같은 이름으로 다시 올리지 않는다. 한 번 배포한 zip 의 해시가 바뀌면 어떤 패키지로 설치된
  워크스페이스인지 되짚을 수 없다. 워크플로도 이미 붙은 zip 을 덮어쓰지 않는다.
- `latest` 같은 별칭 파일을 두지 않는다. 옛 Release 는 지우지 않는다.

## 절차

마운트(Cowork 연결 폴더, 클라우드 동기화 폴더) 밖의 로컬 클론에서 한다. 스테이징을 지우지 못하고
git 잠금 파일이 남기 때문이다.

1. **정본을 옮긴다.** 프로토콜 워크스페이스의 `_context-protocol/` 와 `presets/` 를 클론으로
   복사한다. 위의 "옮기지 않는 것" 은 빼고, `.DS_Store` 같은 잡파일도 뺀다.
2. **패키지 README 를 맞춘다.** `package/README.md` 의 제목과 `- 버전:` 줄, 설치 후 확인 항목,
   수록 프리셋 목록을 이번 버전에 맞춘다.
3. **로컬에서 빌드한다.** `scripts/build.sh [빌드번호]`. 아래를 모두 통과해야 다음으로 간다.
   - 설치기 두 개와 가이드의 `Guide version:` 이 LATEST_VERSION 과 같다
   - 패키지 README 의 버전 표기가 같다
   - 설치기 블록(`<guide_content>`, `<ontology_readme>` 등)이 정본 파일과 일치한다
   - 압축을 풀어 스테이징과 `diff -r` 했을 때 차이가 없다
4. **커밋하고 태그를 push 한다.**

   ```bash
   git add -A && git commit -m "8.3: <바뀐 것 한 줄>"
   git push
   git tag v8.3 && git push origin v8.3
   ```

5. **Release 를 확인한다.** `release` 워크플로가 같은 빌드를 돌려 zip 을 Release 에 붙인다.
   Release 노트에 바뀐 것과 zip 의 sha256 을 적는다. 해시는 워크플로 로그의 마지막 줄에 있다.
6. **프로토콜 워크스페이스에 기록한다.** `dist/protocol-build.md` 빌드 이력에 한 줄(버전, 빌드,
   날짜, sha256 앞 16자, 비고)과 `action-log` 엔트리.

## 워크플로 없이 올릴 때

이미 검증한 zip 을 그대로 올려야 할 때(예: 저장소 이전부터 있던 빌드)는 직접 만든다.

```bash
gh release create v8.2 dist/context-protocol-8.2.zip --title "context-protocol 8.2" --notes-file notes.md
```

워크플로가 그 뒤에 같은 태그로 돌아도 같은 이름의 zip 이 이미 있으면 건너뛴다.
